# 天枢 Agent OS 3.0 组件金字塔与模块职责边界

> 文档编号：TS-AOS-ARCH-020  
> 版本：v1.0 Draft  
> 基线代码：`main@1d72e26b1cc0468c07d145be2f0b7b81dc61bb96`  
> 关联：PR #25、Issue #26  
> 定位：C01—C09 组件分解、模块独立性和依赖治理的权威规范

## 一、审查结论

天枢 Agent OS 3.0 已具备顶层金字塔：产品目标、九个能力组件、工作包、契约、状态机和发布 Gate 已经形成自上而下结构。

当前仍有两个关键缺口：

1. **代码层组件独立性不足**：Engine v2 多个核心类同时承担编排、业务规则、基础设施、持久化和观测职责；
2. **文档层模块粒度不一致**：C01—C09 有时被描述为单一组件，有时实际包含多个不同生命周期的能力，缺少统一的“组件组—有界模块—应用服务—端口—适配器”分层。

本文件冻结以下修正：

- C01—C09 定义为**一级能力组件组**，用于产品能力地图和主链编排；
- 二级有界模块是代码隔离、测试、数据归属和独立演进的最小单元；
- 每个有界模块内部统一使用 Domain、Application、Ports、Adapters、Persistence、Observability 六类职责；
- 跨组件协作只允许经过 Contracts、公开 Port、Domain Event 和 Receipt Ref；
- 新 Agent OS 核心禁止通过全局单例、直接数据库导入或兄弟组件实现路径建立隐式依赖。

## 二、金字塔结构

```text
L0  用户结果与系统目标
    └── 可验证完成、风险受控、失败可恢复、持续进化

L1  Agent OS 主链能力组
    └── C01 → C02 → C03 → C04 → C05 → C06 → C07 → C08 → C09

L2  有界模块
    └── 每个组件组拆成单一能力、单一数据归属、单一生命周期的模块

L3  Application Service / Use Case
    └── 一个服务完成一个用例，不同时承担路由、存储、授权和交付

L4  Ports 与 Contracts
    └── Inbound Command/Query Port、Outbound Repository/Provider/Event Port

L5  Adapters、Persistence 与 Observability
    └── Engine v2、SQLite、Provider、Tool、Memory OS、Connector、Trace、Receipt
```

依赖方向：

```text
Adapters / Infrastructure
        ↓ implements
Ports ← Application → Domain
        ↑ uses contracts
Cross-component public contracts
```

Domain 和 Application 不依赖 SQLite、环境变量、Provider SDK、Connector SDK 或其他组件实现目录。

## 三、独立组件判定标准

一个有界模块同时满足以下六项，才可标记为独立：

| 维度 | 判定要求 |
|---|---|
| 单一职责 | 能用一个动词短语描述，删除后只损失一种核心能力 |
| 数据归属 | 明确拥有的 Aggregate、Projection 和 Repository，禁止写其他模块表 |
| 接口边界 | 具有公开 Inbound/Outbound Port，不暴露内部类和表结构 |
| 失败隔离 | 失败状态、重试、补偿和降级由本模块定义，不隐式改变其他模块状态 |
| 测试独立 | Domain/Application 可使用内存 Port 单测，无需启动完整 Runtime |
| 演进独立 | Schema、Feature Flag、Shadow Diff 和回滚点可单独管理 |

以下任一情况出现，模块应继续拆分：

- 一个类同时负责业务决策、外部执行和持久化；
- 一个方法直接写两个以上组件的数据表；
- 一个组件通过兄弟组件内部文件调用实现；
- 一个 Registry 同时承担发现、授权、执行、审计和结果验证；
- 一个 Router 同时承担输入加工、Provider 选择、持久化和 Outcome；
- 一个 Store 同时负责状态机、领域投影、Trace 和长期记忆写入。

## 四、当前代码批判性审查

### 4.1 `AgentLoop`：主链“上帝对象”

当前 `runtime/src/core/agent-loop.ts` 同时承担：

- ReAct 消息循环；
- 模型调用；
- Tool Schema 生成和工具执行；
- Hook；
- Checkpoint；
- L2 Cycle；
- typecheck/test/lint Gate；
- Artifact Bundle；
- 独立 Reviewer；
- Goal achieved 更新；
- Run/Event 状态写入；
- Token 与重复模式控制。

主要风险：

- C02、C05、C06、C08 的职责集中在一个类；
- 模型停止调用工具会直接影响内层终止，Goal 完成仍由 Gate 全过后直接写入；
- `repairContext:string` 继续承担跨轮状态；
- 单测需要同时模拟模型、工具、数据库、Goal、Gate、Hook 和 Trace。

目标拆分：

```text
AgentLoop
├── LegacyL1Adapter
├── LegacyL2Adapter
├── C06 ExecutionLoop
├── C06 CycleOrchestrator
├── C02 GoalJudgePort
├── C05 ModelExecutionPort
├── C05 ToolExecutionPort
└── X02 Event/Receipt Port
```

`ExecutionCoordinator` 调用各组件，`AgentLoop` 不再拥有主链权威。

### 4.2 `LlmRouter`：路由、上下文和记忆混合

当前 `runtime/src/llm/router.ts` 同时承担：

- Provider 选择；
- fallback；
- Memory Context 构建和 Prompt 注入；
- Usage 写库；
- Interaction 记忆写入；
- Context observe/consume finalize。

目标拆分：

```text

├── ProviderRegistryAdapter
├── ModelExecutorAdapter
└── LegacyLlmRouterAdapter

迁出：
Context 注入        → C03 Context Planner
Route 与 fallback  → C05 Model Broker
Usage               → X03 UsageRepository
Memory Candidate    → C09 Memory Write Gate
Context Consumption → C03/C08 Usage Observation
```

### 4.3 `ToolRegistry`：发现、政策、授权和执行混合

目标拆分：

### 4.4 `MemoryBackendRouter`：Context、写入、Authority 和治理混合

当前 `runtime/src/memory/router.ts` 同时承担：

### 4.5 `EventStore`：状态、事件、投影和记忆触发混合


### 4.6 `GoalManager`：Aggregate、Repository、预算和 Judge 混合

当前 `runtime/src/goal/goal-manager.ts` 同时承担：

- Goal 内存缓存；
- SQLite 序列化和写入；
- Goal 状态机；
- Budget；
- Cycle 消耗；
- 完成度检查；
- Audit Log。

目标拆分：

```text
GoalAggregate
GoalRepository
GoalStateService
GoalBudgetService
GoalProgressService
GoalJudgeService
GoalAuditPort
```

模型和 Legacy Adapter 均不得直接调用 `updateGoal(... achieved ...)`。

### 4.7 直接数据库依赖与全局单例

当前多个模块直接导入 `store/db.ts`，包括 Goal、Memory、Evolve、Cron、Workflow、LLM Usage、Sandbox Audit 等。数据访问方式便捷，但会产生：

- 表结构成为跨模块隐式 API；
- 事务边界分散；
- 测试依赖真实 SQLite；
- 一个 Migration 影响多个业务模块；
- 数据 Owner 无法执行写入约束。

当前还广泛使用 `getXxx()` 和模块级单例。Legacy 路径可以保留，Agent OS 3.0 新路径统一由 Composition Root 注入。

## 六、横切平台模块

横切能力不归属任一业务组件，统一通过 Port 提供：

| 编号 | 平台模块 | 责任 |
|---|---|---|
| X01 Contracts Kernel | Schema、Canonical JSON、Stable Hash、ID、Error |
| X02 Execution & Workflow | Execution、Run、Step、Domain Event、Replay |
| X03 Persistence | Transaction、Repository 基类、Migration、Outbox |
| X04 Observability | Trace、Metric、Log、Receipt Store |
| X05 Runtime Configuration | Feature Flag Snapshot、Capability Snapshot、配置验证 |
| X06 Composition Root | 实例创建、依赖注入、Legacy Adapter 装配 |

横切平台不得吸收领域判断。例如 EventStore 不判断 Goal，ReceiptStore 不判断授权，Configuration 不接受模型输出。

## 七、目录规范

每个组件目录使用统一结构：

```text
runtime/src/<component>/
├── domain/          # Entity、Value Object、纯规则、状态机
├── application/     # Command/Query Handler、Use Case
├── ports/
│   ├── inbound/     # 对 Coordinator 和其他组件公开
│   └── outbound/    # Repository、Provider、Event、Clock 等接口
├── adapters/
│   ├── inbound/     # CLI、Legacy、HTTP、Cron
│   └── outbound/    # SQLite、Provider、Tool、Memory OS、Connector
├── persistence/     # Repository 实现和 Projection
├── observability/   # Receipt、Trace、Metric Adapter
├── public.ts        # 唯一跨组件公开入口
└── internal.ts      # 仅组件内部使用，禁止跨组件导入
```

不是每个组件都需要所有目录；缺失目录可以省略，职责类型不能混放。

## 八、依赖硬规则

### 8.1 跨组件导入

允许：

```text
contracts/*
<component>/public.ts
<component>/ports/inbound/*
Domain Event Schema
Receipt Ref
```

禁止：

```text
<component>/application/*
<component>/domain/*
<component>/persistence/*
<component>/adapters/*
<component>/internal.ts
```

### 8.2 数据访问

- Domain 和 Application 直接导入 `store/db.ts` 的数量必须为 0；
- SQLite 访问只允许在 Persistence/Outbound Adapter；
- 每张业务表只有一个写 Owner；
- 其他组件通过 Query Port、Event 或只读 Projection 获取数据；
- 跨组件事务由 Coordinator + Unit of Work 组织，组件不得私自开启嵌套业务事务。

### 8.3 实例管理

- Agent OS 3.0 新核心禁止模块级可变单例；
- `getXxx()` 仅保留在 Legacy Adapter；
- `agent-os-runtime.ts` 是唯一 Composition Root；
- Clock、ID、Hash、DB、Provider、Tool、Memory Backend 均通过构造器或 Factory 注入。

### 8.4 状态与事件

- 一个状态机只有一个 Owner；
- 其他组件只能提交 Command 或消费 Event；
- 关键状态更新必须绑定 Receipt Ref；
- 反向反馈由 Coordinator 调用 Port，禁止反向实现依赖；

## 十一、架构适应性测试

CI 必须新增：

| Test ID | 阻断条件 |

| ARCH-006 | EventStore、ReceiptStore 吸收领域判断 |
| ARCH-007 | Model Adapter 直接写 Memory |

| ARCH-009 | Delivery 直接写 Outcome Success |

| ARCH-011 | Public Port 缺少 Contract Test |
| ARCH-012 | Legacy Adapter 无删除条件或 Feature Flag |

建议质量阈值：

- 跨组件实现导入：0；
- Domain/Application 直接 DB 导入：0；
- 新核心全局单例：0；
- 外部副作用重复：0；
- 数据 Owner 冲突：0；
- 依赖环：0；
- Public Port Contract Test 覆盖：100%；
- 单类直接依赖超过 8 个时强制架构评审；
- 单类同时承担 3 类以上职责时强制拆分评审。

## 十二、完成定义

一个组件组完成不能只看目录和类是否存在，必须同时满足：

1. 二级有界模块清单完整；
2. 每个模块有单一职责、输入、输出和错误语义；
3. 数据 Owner 和 Repository 明确；
4. 跨组件调用只经过公开 Port；
5. Domain/Application 可用内存 Adapter 独立测试；
6. Shadow、Feature Flag、Receipt 和回滚点可独立控制；
7. 架构适应性测试全部通过；
8. Legacy 大型类只保留兼容入口，不再拥有新主链权威。
