# 天枢 Agent OS 3.0 工程实施总设计

> 文档编号：TS-AOS-ENG-012  
> 版本：v1.0 Draft  
> 关联：PR #25、Issue #27  
> 范围：`AWKN-Lab/tianshu` 单仓实现与 AWKN Memory OS 挂载

## 一、工程结论

Agent OS 3.0 采用“契约先行、适配包裹、双轨验证、逐段接管”的迁移方式。Engine v2 在迁移期持续可运行，新主链通过 `0 | shadow | enforce` 逐组件启用。

本设计冻结以下决定：

1. 新增 `ExecutionCoordinator`，作为 C01—C09 的唯一主链编排器；
2. `ExecutionEnvelope` 由 Trusted Input Gateway 创建，由 Coordinator 按 revision 更新并关闭；
3. Envelope 持久化保存引用、状态、Hash 与 revision，不保存所有组件完整正文；
4. Receipt 使用统一 Envelope 和分类 Payload，写入 `receipts`；
5. EventStore 记录状态变化和领域事件，ReceiptStore 记录“证明材料”；Event 可以引用 Receipt，二者职责分离；
6. Feature Flag 在 Execution 创建时冻结，运行中配置变化不影响已启动 Execution；
7. 现有 `runL1()`、`runL2()`、`LlmRouter.chat()`、`ToolRegistry.execute()`、`compileAndRender()`、`rememberResponse()` 全部保留兼容入口，逐步降级为 Adapter；
8. 除 AWKN Memory OS 外，禁止新增其他 AWKN 业务仓库运行依赖。

## 二、当前基线与主要耦合

### 2.1 AgentLoop

`runtime/src/core/agent-loop.ts` 当前同时承担：

- ReAct 消息循环；
- LLM Router 直连；
- Tool Registry 直连；
- Checkpoint；
- L2 Gate 执行；
- 独立 Reviewer；
- Goal 终态更新；
- Run/Event 写入。

迁移后保留内层工具循环和兼容入口，Goal Judge、Broker、Receipt、Delivery、Outcome 从中拆出。

### 2.2 LlmRouter

`runtime/src/llm/router.ts` 当前同时承担：

- Provider 选择与 fallback；
- Memory Context 注入；
- 使用量记录；
- 成功响应记忆写入；
- Context finalize。

迁移后：

- Provider 路由进入 `ModelBroker`；
- Context 注入由 `ContextPlanner` 产出 `ContextManifest`；
- 记忆候选进入 `MemoryWriteGate`；
- `LlmRouter` 保留 Provider Adapter 和 Engine v2 兼容行为。

### 2.3 数据库

当前 SQLite 主迁移为 v1—v7，附加迁移 v8—v10。Agent OS 3.0 新迁移从 v11 开始，全部通过统一 `schema_migrations` 注册。

## 四、主链与依赖 DAG

```text
Contracts
   ├── Input ──> Intent ──> Goal
   ├── Claim ──> Context ───────┐
   └── Receipt/Event            │
                                ▼
                        Policy + Skill
                                ▼
                       Model + Tool Broker
                                ▼
                         Evidence-Gain Loop
                                ▼
                      Delivery ──> Outcome
                                ▼
                       Memory Write Gate
                                ▼
                             Evolve
```

禁止依赖：

- C01—C05 不得依赖 Delivery、Outcome、Memory Write 或 Evolve；
- Policy 不得调用 Tool；
- Skill 不得修改 Policy；
- Broker 不得生成 Goal 终态；
- Model Adapter 不得直接写长期记忆；
- Delivery 不得把“发送请求成功”升级为业务结果成功；
- Memory OS 不得反向调用天枢 Runtime。

允许回路仅限受控反馈：

- Evidence Loop → Context Planner：`CONTEXT_GAP`；
- Evidence Loop → Broker：`CAPABILITY_GAP`；
- Evidence Loop → Intent/Goal：范围冻结或用户确认；
- Outcome → Evolve：离线候选，不修改当前 Execution。

## 六、ExecutionCoordinator

### 6.1 职责

`ExecutionCoordinator` 负责：

- 创建、加载和关闭 `ExecutionEnvelope`；
- 按主链顺序调用组件；
- 绑定每个组件产物 Ref、Bundle Hash 与 Receipt；
- 执行状态机；
- 恢复 Execution；
- 读取冻结的 Feature Flag Snapshot；
- 生成最终 Execution Summary。

它不负责：

- 自行分类意图；
- 自行选择模型或工具；
- 自行判断 Goal 达成；
- 自行写长期记忆；
- 在事务外修改业务投影。

### 6.2 Envelope 更新

每次更新必须提供：

```ts
interface EnvelopePatchCommand {
  executionId: string;
  expectedRevision: number;
  patch: Record<string, unknown>;
  event: DomainEventInput;
  receiptRefs?: string[];
}
```

更新在同一 SQLite 事务内完成：

```text
验证 expectedRevision
→ 写 Event
→ 更新 Projection
→ 关联 Receipt Ref
→ revision + 1
```

## 七、ReceiptStore 与 EventStore

### EventStore

负责：

- append-only 领域事件；
- Run、Step、Execution 状态重放；
- 事件顺序和幂等；
- Projection 重建。

### ReceiptStore

负责：

- 输入、路由、编译、授权、模型、工具、Gate、交付、结果、记忆和进化证明；
- Canonical Payload Hash；
- Producer、Schema、时间、关联对象；
- 大 Payload 外置 Artifact Ref。

强制规则：

- 关键状态转换必须引用至少一个 Receipt；
- Receipt 写入失败时，不允许提交对应状态；
- 外部副作用采用“Intent Receipt → 外部调用 → Completion Receipt”；
- Event Payload 不复制完整 Receipt Payload。

## 八、Feature Flag 权威来源

优先级从高到低：

1. Execution 创建参数中的受控 override；
2. 天枢部署配置文件；
3. 环境变量；
4. 代码默认值。

禁止：

- Skill 修改 Flag；
- 模型输出修改 Flag；
- 外部文档修改 Flag；
- Execution 运行中热切换已冻结 Flag。

每个 Execution 保存：

```ts
interface FeatureFlagSnapshot {
  schema: 'awkn-feature-flag-snapshot/v1';
  flags: Record<string, '0' | 'shadow' | 'enforce'>;
  sourceHash: string;
  frozenAt: string;
}
```

## 十、PR 拆分与合并顺序

每个 WP 使用独立短分支，推荐拆分：

```text
[Spec] 契约、错误码、状态机
[Store] Schema、Migration、Repository
[Core] 纯逻辑与服务
[Adapter] Engine v2 兼容
[Test] Unit、Contract、Golden、Replay
[Obs] Trace、Metric、Receipt
[Gate] Shadow、回滚、Release 证据
```

合并规则：

1. Spec 先于 Store；
2. Store 先于写路径；
3. Core 可以与只读 Adapter 并行；
4. Shadow 代码合并后保持默认 `0`；
5. Shadow 达标后单独 PR 切 `enforce`；
6. Legacy 删除单独 PR，禁止与新功能同批删除。

## 十一、Owner 角色

仓库未冻结具体人员，先冻结职责角色：

- Architecture Owner：跨组件边界和依赖 DAG；
- Contract Owner：Schema、Canonical JSON、错误码；
- Runtime Owner：Coordinator、AgentLoop Adapter；
- Persistence Owner：Migration、Repository、Replay；
- Policy Owner：Policy/Skill Compiler；
- Broker Owner：Model、Tool、Authorization；
- Memory Protocol Owner：双仓兼容；
- Release Owner：CI、Manifest、RC Gate。

任何接口变更必须由接口 Owner 评审。

## 十二、Windows 与 Linux

必须统一：

- Path 使用 `node:path`，持久化路径使用规范化 POSIX 表达；
- Shell 命令通过 Runner 抽象，禁止依赖 Bash 专属语法；
- SQLite WAL、文件锁、临时目录分别验证；
- 换行符不进入 Stable Hash；
- UTF-8、Unicode NFC 和时区行为一致；
- Windows 长路径和进程退出码进入 Golden Case；
- CI 至少覆盖 Node 20、Windows latest、Ubuntu latest。

## 十三、回滚策略

### 代码回滚

- Flag 从 `enforce` 切回 `shadow` 或 `0`；
- 保留 Engine v2 Adapter，直至 WP19 完成；
- 新写路径必须支持停止，不要求立刻删除新表。

### 数据回滚

- Migration 前创建数据库备份和 Schema Manifest；
- v11—v19 坚持 additive-first；
- 进入新表的数据通过 compatibility projection 供旧路径读取；
- 发生故障时恢复备份，或停用新写路径并保留新表待修复；
- 禁止未经备份执行破坏性列删除。

### 外部副作用回滚

- 有补偿能力的动作写入 Compensation Plan；
- 无补偿能力的动作要求更高授权和幂等键；
- 已发生副作用但本地失败时进入 `SIDE_EFFECT_UNCERTAIN`，禁止自动重试。

## 十四、实施 Gate

### Gate 0：文档冻结

12—18 文档完成，P0 决策有唯一结论。

### Gate 1：Baseline

精确 SHA、安装、测试、性能、依赖和能力清单可复现。

### Gate 2：Contracts

只合并契约、Canonical JSON、Hash、Fixture、Receipt Envelope 和 Contract Test。

### Gate 3：Shadow

按 Input → Intent → Context → Compiler → Broker → Loop → Delivery → Memory 分段 Shadow。

### Gate 4：Enforce

每段满足差异阈值、性能阈值、回滚演练和安全测试后接管。

### Gate 5：RC

全链路 Replay、Windows/Linux、Memory OS Protocol Smoke、Manifest 与 Artifact Hash 完成。

## 十五、Definition of Done

单个 WP 完成必须具备：代码、Schema、Migration、测试、Receipt、Trace、Metric、诊断命令、回滚说明、兼容性报告和精确 Commit 证据。

本文件完成工程拆分，不代表任一代码 WP 已完成。
