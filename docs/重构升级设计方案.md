## 一、现状诊断

### 1.1 awkn引擎 现状

**性质**：纯 prompt/Markdown 配置包，无可执行运行时。

**结构**：
```
awkn引擎/
├── agents/tianhuo/          # 天火 agent 配置（prompt + 记忆 + 流程）
│   ├── agent.prompt          # 启动器（packet/gate/card）
│   ├── 01-身份与行为/        # SOUL/BOUNDARY/IDENTITY
│   ├── 02-流程与规范/        # AGENTS/SOP
│   ├── 03-能力与工具/        # CAPABILITY/TOOLS
│   ├── 04-记忆与知识/        # MEMORY/EXPERIENCE/DECISION
│   └── archive/             # 冷路由索引
└── skills/                   # 60+ 技能插件（SKILL.md）
```

**执行方式**：依赖外部宿主（Claude Code / Codex / Mavis）读取 prompt 后执行，自身没有：
- 可执行的 agent loop
- hook 调度器
- goal 评估器
- cron/schedule 调度器
- 技能加载运行时

### 1.2 awkn-agent 现状

**性质**：完整可执行运行时，4 层架构。

**已实现的 Loop Engineering 对应能力**：

| Claude Code 概念 | awkn-agent 实现 | 文件 |
|------------------|----------------|------|
| Turn-based loop (Skill 验证) | ReAct 循环 + SKILL.md | `src/core/agent-loop*.ts` |
| /goal (停止条件) | GoalManager + 自动评估 | `src/workflow/goal/` + `src/api/routes/goals.ts` |
| /loop /schedule (时间触发) | CronEngine + 上下文快照恢复 | `src/cron/engine.ts` |
| /hook (事件触发) | HookManager (6 lifecycle points) | `src/core/hook-manager.ts` + `src/security/hooks.ts` |
| 动态工作流 (并行 agent) | SwarmOrchestrator | `src/swarm/orchestrator.ts` |
| auto mode (跳过权限) | PermissionEngine + ApprovalGateway | `src/security/permission-engine.ts` |
| token 用量监控 | UsageLedger + UsageObserver | `src/llm/usage-ledger.ts` |
| loop 异常检测 | LoopMonitor (3-strike/重复模式) | `src/core/loop-monitor.ts` |

**问题**：awkn-agent 和 awkn引擎 是两套独立系统，awkn引擎 的天火配置没有把这些能力暴露成可用命令，也没有文档化映射。

### 1.3 核心矛盾

```
awkn引擎 = 配置丰富（60+技能 + 完整agent配置）但无运行时
awkn-agent = 运行时完整（Loop/Hook/Goal/Cron全有）但与awkn引擎脱节
```

3 篇文章讲的是"如何设计 Loop"，awkn-agent 代码层已全部实现，但 awkn引擎 的天火 agent **不知道自己有这些能力**，也无法直接调用。

## 二、Loop Engineering 理念吸收

### 2.1 核心框架（来自3篇文章共识）

**四层自主权递进**：

| 层级 | 交出什么 | 触发方式 | 停止机制 | 适用场景 |
|------|---------|---------|---------|---------|
| L1 Turn-based | 验证步骤 | 用户手动 | 用户判断 | 探索、一次性修改 |
| L2 Goal-based | 停止条件 | 用户手动 | 确定性评估器 | 有明确完成标准 |
| L3 Time-based | 触发时机 | 时间驱动 | 条件满足/手动停 | 周期性、监控 |
| L4 Proactive | 整个决策流程 | 组合驱动 | 多 gate 组合 | 长期无人值守 |

### 2.2 七条铁律（提炼）

1. **确定性优先**：停止条件、验证用确定性标准（测试通过数/分数/报错），不用描述性判断
2. **循环里必须有"说不"的**：测试、类型检查、真实报错、第二 agent review
3. **hook 短平快**：同步阻塞，重活给 Skill 或后台进程
4. **Skill 沉淀"好"的标准**：验证流程、团队规范编码成可复用资产
5. **token 是硬约束**：选对层级、先试水、间隔匹配变化频率、盯用量
6. **先 L2 再 L4**：从 /goal 开始收益最大门槛最低，/loop 和 proactive 等用顺了再说
7. **代码库要干净**：AI 跟着已有模式走，脏代码库会让 loop 放大技术债

## 四、重构升级方案

### 4.1 方案选择：自带轻量 Node.js 运行时（不依赖 awkn-agent）

**决策依据**：awkn-agent 是独立项目，TRAE 等宿主一般不调用它；awkn引擎 必须能独立跑。

**方案**：从 awkn-agent 抽取零业务耦合的纯函数/类型模块，组装成 awkn引擎 自带的轻量运行时。

**可抽取模块清单**（按独立抽取难度排序）：

| 模块 | 源文件 | 抽取难度 | 依赖 |
|------|--------|---------|------|
| ReAct 状态机 | `awkn-agent/src/core/react-loop.ts` | 极低 | 零 |
| hook-types + hook-manager | `awkn-agent/src/core/hook-types.ts` + `hook-manager.ts` | 低 | execFile + logger |
| goal-state + goal-manager | `awkn-agent/src/workflow/goal/goal-state.ts` + `goal-manager.ts` | 低 | 零（纯内存） |
| skills parser + trigger-matcher | `awkn-agent/src/skills/types.ts` + `parser.ts` + `trigger-matcher.ts` | 低 | 零 |
| tools types + registry | `awkn-agent/src/tools/types.ts` + `registry.ts` | 中 | featureFlags（可移除） |
| cron-engine | `awkn-agent/src/cron/engine.ts` | 中 | cron-parser + SQLite |
| agent-loop ReAct 循环 | `awkn-agent/src/core/agent-loop-react-cycle.ts` | 高 | LLM provider + ToolRegistry + hooks（需适配层） |

**抽取原则**：
- 优先复用前 6 个低耦合模块（纯函数/类型）
- agent-loop 循环编排按目标运行时重新实现适配层
- 存储用 SQLite（goals / cron-jobs / loop-state / usage 四张表，单文件 `runtime/data/awkn-engine.db`）
- LLM provider 适配 TRAE 自带 / CODEX / MiniMax 三家（不接 OpenAI/Anthropic 原生 SDK）
- 不反向修改 awkn-agent 源码，只单向抽取

### 4.4 四层 Loop 落地设计

#### L1 Turn-based（默认）

**现有**：天火 `Classify → Fetch → Plan → Execute → Review/Verify → Evolve` 已是 L1。
**升级**：
- Execute 后强制接入 `awkn-执行检查` 的 Verify 步骤作为 Skill 验证
- 验证失败 → Fix 牌 → 再 Execute，不依赖用户手动检查

#### L2 Goal-based（新增）

**命令**：`/goal <意图描述>，验收标准：[hao1, hao2, ...]，最多 N 轮`

**流程**：
```
1. 意图解析（awkn-意图理解）
2. 方案冻结（awkn-spec + awkn-工程文档，防返工）
3. while (未达验收标准 && 轮数 < N):
   a. 跨阶段调度（awkn-程序员天阶功法）
   b. 执行（awkn-工程师）
   c. 质量门禁（awkn-审核）← "说不"
   d. 停止条件评估（确定性：测试通过数/类型检查0错误/lint 0新增）
   e. 未达标准 → 记录失败 → 下一轮
4. 复盘写回（awkn-复盘总结）
```

**停止条件必须是确定性的**：
- `tsc --noEmit` 0 错误
- `vitest run` 0 failed
- `biome check` 0 新增
- 指定测试用例通过
- 不用"代码质量好"这种描述性判断

#### L3 Time-based（新增）

**命令**：`/loop <间隔> <任务描述>` 或 `/schedule <cron> <任务描述>`

**落地**：映射到 awkn-agent 的 CronEngine，天火配置里声明可调度的 cron 任务清单。

**适用**：
- 每日健康检查（跑 awkn-审核 的 6 维度评分）
- 每周复盘（awkn-复盘总结）
- 定时巡检（awkn-执行检查 的 Verify）

#### L4 Proactive（预留，不默认启用）

**条件**：L2 用顺 + 有明确的定型工作流。
**组合**：CronEngine + SwarmOrchestrator + auto mode。
**门禁**：必须经 safetyGate + 用户确认（BOUNDARY.md 已有此规则）。

### 4.5 质量门禁设计（循环里"说不"的东西）

| 门禁 | 检查项 | 不通过动作 |
|------|--------|-----------|
| typecheckGate | `tsc --noEmit` 0 错误 | 打回继续 |
| testGate | `vitest run` 0 failed | 打回继续 |
| lintGate | `biome check` 0 新增 | 打回继续 |
| reviewGate | awkn-审核 PASS/PASS_WITH_RISKS | 打回继续 |
| securityGate | 无密钥泄露/无越权/无危险操作 | 立即中断 |
| verificationGate | 有 fresh evidence | 不得宣称完成 |
| budgetGate | token/轮数未超限 | 停止 loop |

### 4.6 token 控制策略

| 策略 | 落地 |
|------|------|
| 选对层级 | 90% 任务用 L1，有明确标准用 L2，周期性用 L3 |
| 选对模型 | 简单验证用便宜模型，复杂推理用强模型（awkn-agent 已有多 provider） |
| 确定性写脚本 | 重复性验证写成 SKILL.md 脚本，不靠推理 |
| 先小规模试跑 | L4 动态工作流先跑 3-5 个，不一次起几十 |
| 间隔匹配频率 | PR review 一小时一条就别 5 分钟轮询 |
| 盯用量 | 每轮记录 token，超预算停（映射 awkn-agent UsageLedger） |

```typescript
// orchestrator/tianhuo-cicd-loop.ts 核心循环
async function runTianhuoCicdLoop(goalId, taskPrompt) {
  const goal = goalManager.read(goalId);
  while (goal.state === 'active' && cycle < maxCycles) {
    // 1. 天火用 TRAE 规划+执行
    const tianhuoResult = await new AgentLoop({
      cwd, goalId, enableL2: false,
      callSource: 'sub_agent',
      systemPrompt: loadTianhuoPrompt(),
    }).runL1(taskPrompt + feedbackFromLastCycle);

    // 2. 提交产物给 cicd-tester（用 CODEX 跨模型，防互认同）
    const reviewResult = await new AgentLoop({
      cwd, enableL2: false,
      callSource: 'sub_agent',
      provider: 'codex',  // ← 显式指定，绕过 router 默认
      systemPrompt: loadCicdTesterPrompt(),
    }).runL1(`审查以下产物：\n${tianhuoResult.finalText}`);

    // 3. 评估 5 项停止条件（4 项确定性 + cicd-tester PASS）
    const stopEval = await evaluateTianhuoCicdStop({
      cwd, goalId,
      cicdTesterVerdict: parseVerdict(reviewResult.finalText),
    });

    if (stopEval.achieved) {
      goalManager.updateGoal(goalId, { state: 'achieved' });
      return { achieved: true, cycles: cycle };
    }

    // 4. 打回原因回填给天火，下一轮
    feedbackFromLastCycle = reviewResult.finalText;
    cycle++;
  }
}
```

**B.3 关键算法：PRD 一致性评估**

```typescript
// gates/prd-consistency.ts
//
// 算法思路：
// 1. 从 PRD 抽取"关键需求项"（用户故事 + 验收标准），每项算一个 hash
// 2. 从当前产出（执行计划 + 工程文档）抽取"已覆盖项"，每项算一个 hash
// 3. 一致性 = |交集| / |PRD关键需求|
// 4. < 0.8 → 打回，输出未覆盖清单

interface PrdRequirement {
  id: string;          // US-001 / AC-002
  text: string;        // 原文
  hash: string;        // sha256(text).slice(16)
  covered: boolean;    // 是否在产出中找到对应
  coverageProof?: string;
}

function evaluatePrdConsistency(prd: string, artifacts: string[]): {
  consistency: number;        // 0..1
  passed: boolean;            // consistency >= 0.8
  uncovered: PrdRequirement[];// 未覆盖清单，回填给下轮
} {
  const prdReqs = extractRequirements(prd);     // 正则抽 US-/AC-
  const artifactHashes = new Set<string>();
  for (const a of artifacts) {
    for (const line of a.split('\n')) {
      artifactHashes.add(hash(line.trim()));
    }
  }

  const uncovered: PrdRequirement[] = [];
  for (const req of prdReqs) {
    // 匹配策略：hash 精确匹配 OR 关键词包含
    req.covered = artifactHashes.has(req.hash)
      || artifacts.some(a => a.includes(req.id) || a.includes(req.text.slice(0, 20)));
    if (!req.covered) uncovered.push(req);
  }

  const consistency = prdReqs.length === 0 ? 1 : (prdReqs.length - uncovered.length) / prdReqs.length;
  return {
    consistency,
    passed: consistency >= 0.8,
    uncovered,
  };
}

function extractRequirements(prd: string): PrdRequirement[] {
  const reqs: PrdRequirement[] = [];
  // 匹配 "US-001: ..." / "AC-002: ..." / "验收标准: ..."
  const patterns = [
    /(?:^|\n)(US-\d+)\s*[:：]\s*(.+)/g,
    /(?:^|\n)(AC-\d+)\s*[:：]\s*(.+)/g,
    /(?:^|\n)验收标准\s*[:：]\s*(.+)/g,
  ];
  for (const p of patterns) {
    let m;
    while ((m = p.exec(prd)) !== null) {
      const id = m[1] ?? `REQ-${reqs.length + 1}`;
      const text = m[2] ?? m[1];
      reqs.push({ id, text, hash: hash(text), covered: false });
    }
  }
  return reqs;
}
```

```typescript
// orchestrator/prd-centric-loop.ts
async function runPrdCentricLoop(goalId, originalGoal) {
  // Phase 1: 目标 → PRD（一次性）
  const prd = await skillTool.execute({
    skill: 'awkn-prd',
    input: originalGoal,
  });

  let cycle = 0;
  while (cycle < maxCycles) {
    cycle++;

    // Phase 2a: PRD → 执行计划
    const plan = await skillTool.execute({
      skill: 'awkn-spec',
      input: `基于以下 PRD 生成执行计划：\n${prd}`,
    });

    // Phase 2b: 计划 → 工程文档
    const docs = await skillTool.execute({
      skill: 'awkn-工程文档',
      input: `基于以下执行计划生成工程文档：\n${plan}`,
    });

    // Phase 2c: 自评 PRD 一致性
    const consistency = evaluatePrdConsistency(prd, [plan, docs]);
    const review = await skillTool.execute({
      skill: 'awkn-审核',
      input: `审查计划与文档是否符合 PRD：\n${prd}\n---\n${plan}\n---\n${docs}`,
    });

    // Phase 2d: 一致性 < 0.8 → 打回
    if (consistency.passed && parseReviewVerdict(review) === 'PASS') {
      // Phase 3: PRD 一致 → 标记 achieved
      goalManager.updateGoal(goalId, { state: 'achieved' });
      await skillTool.execute({ skill: 'awkn-复盘总结', input: ... });
      return { achieved: true, cycles: cycle, consistency };
    }

    // 未达标，把缺口回填给下一轮
    logger.info(`PRD 一致性 ${(consistency.consistency * 100).toFixed(0)}%，未覆盖：${consistency.uncovered.length} 项`);
  }

  return { achieved: false, cycles: cycle, reason: '达到最大循环数' };
}
```

**bug 模式分类扩展**：本轮新增 1 种新 bug 模式："纯函数返回值被丢弃"（3 个实例）。累计 bug 模式分类：假成功 12 / 假失败 2 / 无信号 2 / 资源生命周期错配 2 / 无限挂起 1 / 无输入被当作已处理 2 / 解析不一致 1 / 防御性缺失 1 / 注释/代码不一致 1 / 假完成 1 / 纯函数返回值被丢弃 3 / 子循环 terminated 不检查 1。

#### M3 进阶-29：cron engine stop() 后 zombie timer 泄漏 — medium（latent）

**问题**（`cron/engine.ts` scheduleJob）：`CronEngine.stop()` 设置 `running=false` + `clearTimeout` 所有已注册 timer，但若 job 的 setTimeout callback 正在执行（`await executeJob` 中），callback 完成后调用 `scheduleJob` 调度新 timer → `scheduleJob` 不检查 `running` → 新 timer 加入已清空的 `this.timers` → delay 后触发 executeJob → 无限链式调度 → "假停止"（running=false 但 timer 持续触发）。

**当前未触发原因**：CLI `cron start` 在 `stopCronEngine()` 后立即 `process.exit(0)`，进程死亡使 zombie timer 无意义。但编程式用法会暴露。

**修复**：
1. `scheduleJob` 开头加 `if (!this.running) return;` — 阻断 stop 后的新调度
2. setTimeout callback 开头加 `if (!this.running) return;` — 双重保险（clearTimeout 无法取消已被事件循环拾取的 callback）

**manual override 例外**：`triggerJob`（手动触发）不检查 `running` — 用户显式触发是 override，应能在 stopped 状态执行。

**验证**：tsc 0 errors / verify-cron-stop-no-zombie.ts 13 项通过（静态 6 + 行为 7）/ 全量回归 22 verify + cron unit 18 = 40/40 通过。

**新增候选铁律**：
- **E103（候选）**：状态标志变更必须阻断后续调度，不能只清理已注册的调度。`stop()` 必须同时：①设状态标志 ②清理已注册调度 ③在调度入口检查状态标志。只做①②不做③ → "假停止"。与 E98（系统级状态转换不检查状态机）同源 — 状态标志变为"装饰"而非"门禁"。

**问题**（`llm/providers/codex.ts` + `minimax.ts`）：`content: choice.message.content ?? ''` 不验证空 content — 若 API 返回空 content 且无 tool_calls（content_filter / 限流 200 空体 / API bug），agent-loop break → `finalText=''` `terminated=false` → 假成功。
