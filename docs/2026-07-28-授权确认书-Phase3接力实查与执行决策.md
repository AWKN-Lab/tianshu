## 二、决策树与推荐答案

### D1：本地分支与 PR #64 的对齐策略

**问题**：本地 `feat/phase3-migration-backup-restore` 没有 PR #64 代码，如何对齐？

**选项**：
- **A（推荐）**：将 `tianshu/feat/aos-05b-context-render` merge 到当前分支
  - 理由：保留 PR #64 的 276 个测试证据 + Phase 3 可基于完整代码构建 + 不破坏 PR #64 分支
  - 风险：merge commit 会让 PR #64 分支历史变复杂（但 PR #64 计划 squash merge，不影响）
- B：cherry-pick Phase 3 到 `feat/aos-05b-context-render`
  - 风险：污染 PR #64 分支，违背"PR #64 不接 Runtime 主链"的架构边界声明
- C：保持分支分离，最后各自 squash 到 main
  - 风险：Phase 3 测试无法验证与 Phase 2 的集成

**推荐**：**A**。Merge 远端分支到本地，保留两边证据独立可追溯。

### D2：Phase 3 测试 bug 修复方式

**问题**：3 个失败测试如何修复？

**选项**：
- **A（推荐）**：
  1. 修复 `listMigrationBackups` 时间戳解析：直接用文件 `stat.mtime` 作为 `createdAt`，不依赖文件名解析（文件名只用于排序）
  2. 修复 `skips backup for in-memory databases` 测试：用 `':memory:'` 作为 dbPath，而非创建文件 DB
  3. `cleanupOldBackups` 测试会随 #1 自动通过
- B：删除失败的测试，只保留通过的
  - 风险：降低覆盖率，违背"证据优先"原则

**推荐**：**A**。修复代码与测试，不掩盖问题。
