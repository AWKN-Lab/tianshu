### 1.4 Migration backup/restore 实查

**已实现**（`runtime/src/store/migration-backup.ts`）：
- `backupBeforeMigration()`：WAL checkpoint + 文件 copy + SHA256 hash + `.sha256` 文件
- `restoreFromBackup()`：hash 校验 + displaced 重命名 + copy 回原位 + 二次 hash 校验
- `listMigrationBackups()`：按文件名时间戳排序（code point 比较，不用 localeCompare）
- `cleanupOldBackups()`：保留最近 N 个
- `MigrationBackupError`：4 个错误码（BACKUP_FAILED / RESTORE_FAILED / HASH_MISMATCH / BACKUP_NOT_FOUND）
- Windows transient lock retry（EBUSY/EACCES 重试）

**已接入**：
- `agent-os-migration-registry.ts`：`backupBeforeMigration()` 在 `applyAgentOsMigrations` 前调用
- `getLastMigrationBackup()` / `resetLastMigrationBackup()`：暴露给外部 restore 操作
- 12 个测试覆盖：backup、restore、hash 校验、list、cleanup、round-trip drill、in-memory 跳过

**3 缺口**：
1. **CLI restore 入口缺失**：`bin/awkn-engine.js` 和 `src/cli.ts` 没有 restore 命令；用户无 CLI 工具触发 restore

### 决策 C：Migration 3 缺口实施方案

#### C1. CLI restore 入口

**现状**：`bin/awkn-engine.js` / `src/cli.ts` 没有 restore 命令。

**选项**：
- **C1a 加 `migrate` 子命令到 cli.ts（推荐 ⭐）**：
  - 子命令：`migrate list-backups`、`migrate restore-latest`、`migrate restore --backup <path>`、`migrate status`
  - 破坏性操作要求 `--confirm` 标志
  - 与现有 cli.ts 风格一致
- **C1b 单独 `migration-cli.ts` 入口**：
  - 优点：隔离
  - 缺点：分裂入口
- **C1c 不加 CLI，仅暴露 API**：
  - 风险：用户无法在灾难时 restore

**推荐**：**C1a 加 migrate 子命令**，包含 4 个子操作。

#### C2. cleanupOldBackups 接入生产代码

**现状**：只在测试中调用，生产 migration 完成后不自动清理。

**选项**：
- **C2a 在 applyAgentOsMigrations 全部成功后调用 cleanup（推荐 ⭐）**：
  - 保留最近 5 个备份（可配置 `AWKN_MIGRATION_BACKUP_KEEP` 环境变量）
  - 仅在所有 migration 成功后调用，失败时不 cleanup（保留现场）
- **C2b 在 backupBeforeMigration 完成后立即 cleanup**：
  - 缺点：可能误删刚创建的备份
- **C2c 不接入，手动调用**：
  - 风险：备份无限增长

**推荐**：**C2a 在 migration 全部成功后调用 cleanup**，保留 5 个备份。

#### C3. migration 失败自动 restore

**现状**：`applyAgentOsMigrations` 无 try/catch，失败时直接抛出，DB 处于半迁移状态。

**选项**：
- **C3a 全部回滚到 backup 状态（推荐 ⭐）**：
  - 用 try/catch 包裹 migration loop
  - 失败时：关闭 db → restoreFromBackup(lastMigrationBackup) → 抛出原始错误
  - 优点：安全，DB 状态确定（恢复到 migration 前）
  - 缺点：已成功的 migration 也被回滚（但可重试）
- **C3b 只记录失败，不自动 restore**：
  - 优点：保留现场便于调试
  - 缺点：DB 可能处于不可用状态，下游功能异常
- **C3c 只在最后一个 migration 失败时 restore**：
  - 优点：折中
  - 缺点：逻辑复杂，边界判断困难

**推荐**：**C3a 全部回滚**，最安全。失败时记录日志 + restore + 抛出错误，调用方决定是否重试。

**实施细节**：
- 注意：restoreFromBackup 需要 db 已关闭（文件锁问题）
- 在 try/catch 中：先 db.close()，再 restore，再抛出错误
- 错误信息：`Migration failed: ${originalError.message}; database restored from backup ${backup.backupPath}`
- 新增测试覆盖：migration 失败 → 自动 restore → DB 状态恢复

## 四、风险与边界

### 4.1 Migration 自动 restore 的边界

**风险**：restoreFromBackup 需要 db 已关闭。如果在 try/catch 中 db 未关闭就 restore，会失败。

**缓解**：在 catch 块中先 `db.close()` 再 restore。如果 db.close() 也失败，记录错误但仍尝试 restore。

**边界**：
- 仅当 `lastMigrationBackup !== null` 时才 restore
- in-memory DB 不创建 backup，因此不 restore
- restore 失败时记录错误但不掩盖原始 migration 错误

### 4.2 CLI restore 误操作

**风险**：用户误运行 `migrate restore-latest` 覆盖当前 DB。

**缓解**：
- 要求 `--confirm` 标志
- restore 前显示备份信息（创建时间、pending migrations、hash）让用户确认
- restore 后保留 displaced 文件用于反悔

### 4.3 cleanup 误删

**风险**：cleanupOldBackups 误删最近备份。

**缓解**：
- 默认保留 5 个（够多）
- 仅在 migration 全部成功后调用（不删失败现场的备份）
- 通过 `AWKN_MIGRATION_BACKUP_KEEP` 环境变量可调整
