# Runtime ↔ 宿主 LLM 通信方案分析

> 日期：2026-07-10
> 状态：已归档
> 结论：文件协议桥接是唯一可行方案，外部 API 优先 + 文件桥接 fallback 是推荐策略

---

## 一、背景

awkn引擎 runtime 是纯本地 Node.js 进程，需要调用 LLM 完成任务。有三条潜在通信路径：

1. **TRAE 宿主 LLM**：runtime 运行在 TRAE IDE 内，理论上可调用宿主 LLM
2. **外部 LLM API**：MiniMax / CODEX（OpenAI 兼容）等，通过 HTTP fetch 出站调用
3. **本地文件桥接**：runtime 写 req 文件 → 宿主读 req 写 resp → runtime 读 resp

本文档分析所有可行与不可行的方案，作为架构决策依据。

---

## 二、已排除的方案

### 2.1 MCP（Model Context Protocol）

**结论：不可行**

| 维度 | 分析 |
|------|------|
| 架构方向 | TRAE IDE/CLI 是 MCP **客户端**（连接外部 MCP server），不是 MCP **服务端** |
| runtime 依赖 | runtime 无 `@modelcontextprotocol/sdk` 依赖 |
| 调用方向 | MCP 是"客户端调服务端工具"，而我们需要的是"runtime 调宿主 LLM"，方向反了 |
| 结论 | 即使 runtime 实现 MCP server，TRAE 也不会作为客户端来调用它 |

### 2.2 ACP / 智能体接口

**结论：不可行**

| 维度 | 分析 |
|------|------|
| traecli | 未安装，无法通过 CLI 接口与 TRAE IDE 交互 |
| ACP 接口 | TRAE IDE 不暴露 ACP（Agent Communication Protocol）接口给外部进程 |
| 智能体 API | TRAE 无公开的"智能体调用 API"，宿主 LLM 只能通过用户交互访问 |
| 结论 | 无法通过程序化方式调用 TRAE 宿主的 AI 能力 |

### 2.3 WebSocket

**结论：技术上可行但收益有限，不推荐**

- 需在 runtime 中添加 `ws` 依赖，创建 WebSocket 服务器
- TRAE 宿主侧需要 WebSocket 客户端（但 TRAE skill 无法常驻连接）
- 仍然需要用户手动触发处理，只是传输层从文件换成 socket
- 复杂度增加但核心痛点（手动触发）未解决

### 2.4 HTTP 服务器

**结论：技术上可行但场景受限，不推荐**

- 需在 runtime 中添加 `express`/`http` 依赖，创建本地 HTTP 服务器
- 暴露 `POST /chat` 端点，外部进程可调用
- 但 TRAE 宿主 LLM 仍无法被程序化调用（核心约束未变）
- 仅适用于：runtime 作为 LLM 代理服务器，供其他外部进程调用
- 解决的不是当前问题（当前问题是 runtime 需要调宿主 LLM，不是宿主调 runtime）

### 2.5 文件系统监听（TRAE 侧）

**结论：技术上可行但 TRAE 侧无法实现**

- runtime 侧可用 `fs.watch`/`chokidar` 监听 resp 文件出现（替代 2s 轮询）
- 但 TRAE 侧无法常驻监听 req 文件（skill 是一次性执行，无法后台运行）
- 部分推荐：runtime 侧可改用 fs.watch 替代轮询（降低延迟），但 TRAE 侧仍需手动触发

## 三、可行方案

### 3.1 文件协议桥接（当前实现）

**结论：可行，已实现，是 TRAE 宿主 LLM 的唯一通道**

**架构**：
```
runtime (Node.js)                    TRAE 宿主 (AI 助手)
  │                                    │
  │ 1. trae provider.chat()            │
  │ 2. 写 req-{id}.json ──────────────→│
  │ 3. 轮询 resp-{id}.json (每 2s)     │
  │                                    │ 4. 用户触发 awkn-llm-bridge skill
  │                                    │ 5. AI 读 req → 用 LLM 能力响应 → 写 resp
  │ ←────────────── resp-{id}.json ────│
  │ 6. 读取 resp → 返回给 agent-loop   │
  │ 7. 删除 resp 文件                   │
```

**三层 fallback**（`runtime/src/llm/providers/trae.ts`）：
1. **L1 — pre_llm_call hook**：通过 `hookManager.trigger('pre_llm_call')` 调用注册的 hook，如果 hook 返回 `llmResponse` 则直接返回（快速路径）
2. **L2 — 文件协议桥接**：写 `req-{uuid}.json` → 轮询 `resp-{uuid}.json`（2s 间隔，120s 超时）
3. **L3 — stub 兜底**：返回占位文本，保证不崩溃

**关键约束**：
- resp 文件的 `content` 字段不能含字面换行符，必须用 `\n` 转义
- TRAE 侧需用户手动触发 `awkn-llm-bridge` skill
- 一次只处理一个 req 文件（避免 LLM 上下文混乱）
- 超过 5 分钟的 req 文件视为超时

**补强措施**（2026-07-10 实施）：
- trae.ts 增加防御性 JSON 修复（自动转义 content 中的字面换行符）
- awkn-llm-bridge SKILL.md 增加格式约束警告
- cli.ts 实现 `hook register` 子命令（支持 command 类型 hook 注册）
- cli.ts 增加 `AWKN_LLM_HOOK_SCRIPT` 环境变量入口（L1 hook 自动注册）
- 创建 `runtime/scripts/bridge-monitor.ts` 桥接监控脚本

### 3.2 外部 LLM API（推荐主力）

**结论：最实际的解决方案，推荐作为主力 provider**

- 使用 MiniMax/CODEX 等 OpenAI 兼容 API 作为主要 LLM 来源
- 文件桥接仅作为 TRAE 宿主 LLM 的访问通道（fallback 或特定场景）
- 跨模型 review 通过不同 provider 实现（minimax vs trae）
- 当前架构已支持，只需修复 key 配置

**Provider 策略**：
| 场景 | 推荐 provider | 原因 |
|------|--------------|------|
| 日常任务（L1/L2 循环） | minimax | 全自动，无需手动协调 |
| 跨模型 review | 天火=minimax, cicd-tester=trae | 不同 provider 避免同模型互认同 |
| 无外部 API 时 | trae 文件桥接 | 手动协调，作为 fallback |
| 高速分类/压缩 | minimax | callSource 路由到 highspeed 模型 |

### 3.3 桥接守护进程（可选增强）

**结论：可消除手动触发的最佳方案，待 MiniMax key 修复后实现**

- 创建 `runtime/scripts/bridge-daemon.ts` 常驻进程
- 监听 llm-bridge 目录，发现 req 文件时自动调用 MiniMax/CODEX API 生成响应
- 写回 resp 文件，实现"自动桥接"
- 相当于把文件桥接的"宿主侧处理"从人工换成自动（用外部 API）
- 适用于：runtime 跑长时间循环时，不想手动触发 skill 的场景

---

## 四、决策总结

| 决策 | 理由 |
|------|------|
| 文件桥接作为 TRAE 宿主 LLM 的唯一通道 | MCP/ACP 不可行，文件系统是唯一共享通道 |
| 外部 API 优先策略 | MiniMax key 修复后，默认用 minimax，trae 桥接降级为 fallback |
| 不引入网络依赖 | 保持 runtime 的"纯本地"架构，不加 ws/express/http |
| 桥接守护进程为可选增强 | 如果手动协调可接受，则不实现守护进程 |
| pre_llm_call hook 通过环境变量注册 | `AWKN_LLM_HOOK_SCRIPT` 指向的脚本接收 stdin（请求 JSON），输出 stdout（响应 JSON） |
