## 3. 批判性诊断

### 3.1 P0：工作区不可复现，控制面资产处于半接线状态

本地 `agents/tianhuo/config.json` 已改为引用：

- `../../skills`；
- `../../capabilities`；
- `awkn_tianhuo_start / advance / status`。

但 `capabilities/` 的 38 个文件仍未跟踪。当前机器能运行，不代表 fresh clone、CI 或另一台 IDE 能运行。若只提交配置而漏交 capabilities，路由会在部署后失效；若把全部本地资产一次性提交，又会把约 40 万字的参考资料和部署遗留档案混入 Agent OS R2 主线。

根因：控制面迁移缺少明确的“源码、生成物、运行数据、外部资产”边界。

### 3.2 P0：质量门禁存在“表面统一、实际分叉”

当前至少有四条测试路径：

1. `npm run check` → Architecture + Typecheck + 重复 Typecheck + Node test；
2. `npm run test:vitest` → 确定失败；
3. 23 个 `test/verify-*.ts` → 默认不执行；
4. `agents/tianhuo/scripts/check-runtime-contract.js` → 默认不执行。

主要问题：

- `lint` 等于 `tsc --noEmit`，没有真实 lint；
- `build` 不在 `check` 中，无法证明可发布产物可生成；
- Vitest 4 与现有 `node:test` 测试范式不兼容；
- `vitest.config.ts` 使用已移除的 `test.poolOptions`；
- 修改过的 `verify-skill-tool-terminated.ts` 虽手工通过 19/19，但不会被 CI 自动发现；
- CI 只监听 `runtime/**` 与 workflow，自身不会因 `agents/**`、`capabilities/**`、关键文档变更而触发。

根因：项目同时保留了历史验证脚本、Node test 和未完成的 Vitest 迁移，但没有确定唯一权威入口。

### 3.3 P0：迁移会自动写库，但恢复能力没有跟上

`getDb()` 打开数据库后会立即执行 v1—v12 Migration。当前实现具备单次 migration 的 SQLite 事务保护，但缺少：

- 迁移前数据库备份；
- Schema Manifest 与数据库文件 Hash；
- 磁盘空间和写权限预检；
- Migration dry-run / plan；
- 已提交迁移后的恢复工具；
- 真实旧库样本的升级与恢复演练证据。

文档已经明确要求 backup、restore 或 forward-fix，但运行时没有强制执行。进入 Shadow 前必须补齐，因为 Shadow 会开始生成新的 Decision Artifact 和持久化选择。

### 3.4 P0：安全策略与交付策略互相冲突

本地改动新增了 GitHub Actions 命令拦截，并依赖被 `.gitignore` 排除的 `.trae/hooks/tianshu-hook.mjs`；与此同时，仓库的 R0 基线明确以 GitHub Actions 三平台 CI 为权威证据。

这会造成三种风险：

- 本地 Agent 不能管理或诊断 GitHub Actions，但发布计划又依赖其证据；
- 测试依赖 ignored hook，fresh clone 无法重现；
- “禁止 GitHub Actions”把 CI 检查与生产部署混为同一风险等级。

建议决策：

- 保留 GitHub Actions 作为跨平台只读验证与 Evidence 生成通道；
- 禁止的是未经批准的生产部署、workflow dispatch、workflow 文件写入和危险 API mutation；
- 允许 `gh pr view`、`gh run view`、`gh run download` 等只读诊断；
- TRAE/Codex/CLI 的安全规则必须落在仓库可版本化的统一 Policy Contract 中，不能只存在于 ignored IDE hook。

### 3.5 P1：R2 最大缺口是集成，不是组件实现

WP02—05A 的函数和契约已经成熟，但 Engine v2 的 `AgentLoop`、`LlmRouter`、`GoalManager`、`ToolRegistry` 仍是事实执行权威。没有 Composition Root 把新 Ports 组织成只读 Shadow 链，也没有：

- Execution 创建时冻结的 Feature Flag；
- Engine v2 与 Agent OS 的 Decision Diff；
- Shadow Artifact 持久化；
- 跨平台 Replay Hash；
- R2 Exit Report。

如果跳过 Shadow 直接接入 Enforce，问题会从“可比较”变成“难回滚”。

### 3.6 P1：五个已知旧路径风险仍然真实存在

1. `MemoryBackendRouter.compileAndRender()` 捕获所有错误并回退本地，认证/授权/协议错误仍可能被错误降级；
2. `LlmRouter.enrichWithMemory()` 再次 catch-all 并无记忆继续运行，进一步放大 fail-open；
3. Legacy `GoalManager` 仍允许 model 请求 `achieved`，Deterministic Goal Judge 尚未成为唯一终态权威；
4. `EventStore` 仍直接触发 Memory 路径，Outcome 与 Memory Write Gate 未隔离；
5. `AgentLoop`、`LlmRouter`、`ToolRegistry` 仍是大型聚合点，分别混合编排、Provider/Memory/Usage、Catalog/Policy/Approval/Sandbox/Audit。

这些风险不是立刻全部重写的理由；它们应分别由 WP08—WP16 和 WP19 按 Port + Adapter + Shadow 逐步替换。

### 3.7 P1：本地运行数据存在误提交与隐私泄露面

当前未跟踪内容包括：

- `runtime/data/traces.jsonl`，含 token/tool-call 信号；
- `runtime/runtime/data/llm-bridge/req-*.json`，含 prompt 信号；
- `logs/skills-link-finalize.log`；
- Memory outbox 与派生 Experience。

`.gitignore` 只覆盖 `runtime/data/llm-bridge/`，没有覆盖嵌套的 `runtime/runtime/data/llm-bridge/`、`*.jsonl` 和根 `logs/`。这不是代码功能错误，但属于高概率供应链/隐私事故入口。

### 3.8 P1：Release Evidence 已过期

`runtime/baseline/agent-os-3.0-baseline.json` 的源码基线仍是 `1d72e26`，记录 69 个 TS 文件和 140 个测试；当前已扫描 115 个 TS 文件，工作区执行 275 个测试。CI 上传“新扫描报告 + 旧 baseline JSON”，会制造证据版本不一致。

Baseline 应是不可变历史证据；当前版本应新增新的 evidence manifest，而不是静默覆盖旧基线。

## 4. 目标架构与执行边界

目标主链保持项目已冻结的顺序：

```text
Trusted Input
→ Intent / Goal
→ Claim Ledger
→ Context Planner / Immutable Render
→ Policy / Skill Compiler
→ Model / Tool Broker
→ Evidence-Gain Loop
→ Delivery Router
→ Evidence / Outcome
→ Memory Write Gate
→ Evolve
```

强制边界：

1. `ExecutionCoordinator` 只编排 Public Port，不直接导入兄弟实现；
2. Domain/Application 不读取环境变量、不直接打开 SQLite；
3. Feature Flag 在 Execution 创建时冻结，运行中不可漂移；
4. Shadow 禁止外部写、Delivery、Memory Write 和 Evolve Promotion；
5. Goal `ACHIEVED` 只能由 Goal Judge 生成；
6. Auth、Grant、Protocol incompatibility 必须 fail-closed；
7. 所有新状态变更必须产出 Domain Event 与 Receipt Ref；
8. 每个工作包先交 Contract/In-memory，再独立交 Persistence Migration；
9. 每个可回滚开关都必须有“关闭后的真实验证”，不能只有配置项。

### Phase 4：R2 Trusted Decision Shadow Integration（3—5 天）

对应 Issue #66。

建议新增结构：

```text
runtime/src/execution/
  application/execution-coordinator.ts
  ports/inbound/execute-request-port.ts
  ports/outbound/decision-artifact-store-port.ts
  adapters/engine-v2-shadow-adapter.ts
  adapters/sqlite-decision-artifact-store.ts
  public.ts
```

数据流：

```text
Raw Input
├─ Engine v2：保持原执行和输出
└─ Agent OS Shadow：Trusted Input → Intent → Goal → Claim → Context → Render
                                      ↓
                              Decision Artifact + Diff
```

实现约束：

- Shadow 接收与 Engine v2 相同的原始输入和冻结配置；
- Shadow 只写内部 Decision Artifact，不调用工具、不发送消息、不写 Memory、不改变 Goal；
- 401/403、Grant 缺失、协议不兼容必须分类为 P0 Diff 且 fail-closed；
- Diff 至少分为 `P0_SECURITY / P1_SEMANTIC / P2_EXPECTED / INFRA`；
- Context Manifest/Render 必须可通过 Receipt Ref 重放；
- Feature Flag 支持全局关闭与按 Execution 固化；
- Persistence 版本决定必须先于代码写库，必要时独立 v13 Migration PR。

验收：

- 100% Shadow 无外部副作用；
- Windows/Linux Replay Hash 一致；
- P0 Diff 为 0 才允许 R2 Exit；
- P1 Diff 有阈值、归因和豁免到期日；
- 一键关闭 Shadow 后 Engine v2 行为不变；
- 生成 R2 Exit Report，并由 Issue #43 记录 Go/No-Go。

回滚：关闭 Shadow Flag；保留已生成 Artifact 供分析，Engine v2 不回滚。

```text
→ Enforce Decision
```

WP06 必须满足：稳定 Bundle Hash、Conflict/Unknown/Deny fail-closed、无 DB 直连、无 singleton。

WP07 负责清除 Architecture Scan 中唯一 Legacy Exception `skills/manager.ts`，并把当前 capabilities manifest 演化为正式 Skill Registry 输入，而不是再造第二套清单。

WP08 把 Provider 选择、Fallback、Memory enrichment、Usage persistence 从 `LlmRouter` 拆到 Port/Adapter；认证与协议错误不得 fallback。

WP09 把 Catalog、Policy、Approval、Execution、Sandbox、Audit 从 `ToolRegistry` 分离；GitHub/Deploy 权限在 Policy Bundle 中表达。

WP10 将 `AgentLoop` 的停止条件改为 Evidence Delta、No-Gain、Budget、Goal Judge 四类确定性信号，逐步取消模型自报完成。

R3 Exit：新执行内核在 Shadow 中稳定，至少一个低风险流量类型可受控 Enforce，并可在一分钟内回退 Engine v2。

### Phase 6：R4 Outcome & Memory Loop（约 2 周）

顺序：WP11 Delivery → WP12 Evidence/Outcome → WP13 Memory Write Gate → WP14 Evolve v2。

关键闭环：

- Delivery 必须有 Verification、Retry、Compensation；
- Outcome 必须引用独立 Evidence，不能只引用模型文本；
- Memory 写入先生成 Candidate，再经过敏感度、保留期、用途与授权判断；
- Evolve Promotion 必须经过 Replay，失败进入 Quarantine，可恢复上一版本；
- EventStore 不再直接调用 MemoryService，改由 Outcome/Memory Port 驱动；
- 所有外部副作用都绑定 idempotency key 和 Receipt。

R4 Exit：一次完整执行可以从 Input 重放到 Outcome、Memory Decision 和 Evolution Candidate，且任一外部写都有补偿路径。

- WP18 Observability / Benchmark / Release Evidence；
- WP19 RC、Migration 演练、Legacy Removal。

发布门槛：

- Shadow 指标达到阈值；

- Release Manifest 引用 commit、SBOM、audit、test、migration、benchmark、rollback evidence；
- Canary 成功后才扩大流量。

## 6. 单工作包闭环模板

每个 Issue/PR 必须走完以下闭环，缺一步不得关闭：

1. **Intake**：目标、非目标、风险级别、数据 Owner、前置依赖；
2. **Contract**：Schema、Public Port、Error/Event/Receipt；
3. **Acceptance**：Given/When/Then 与可机验阈值；
4. **Implementation**：Domain/Application/Adapter 分层；
5. **Local Evidence**：类型、lint、unit、contract、build；
6. **Independent Review**：语义、安全、迁移、回滚四类检查；
7. **CI Evidence**：支持矩阵、commit SHA、artifact digest；
8. **Shadow Evidence**：Diff、Replay、无副作用证明；
9. **Merge**：Squash、Issue 关联、Release Evidence Index 更新；
10. **Post-merge**：main 新鲜验证，不复用 PR 旧结果；
11. **Observe**：错误率、P0/P1 Diff、Latency/Token、fallback、rollback readiness；
12. **Close**：文档状态更新、遗留项建 Issue、经验进入 Replay 后再晋级。

## 9. Definition of Done

一个工作包只有同时满足以下条件才能标记 Done：

- 代码、Contract、Migration、文档状态一致；
- 默认门禁和相关扩展门禁均成功；
- 没有新增 Architecture Blocking Violation；
- 数据 Owner、写权限、Error、Event、Receipt 明确；
- 回滚动作已执行验证，不是只写在文档里；
- Shadow/Enforce 状态与 Feature Flag 可观察；
- main 上完成新鲜验证；
- Evidence 与 commit SHA 绑定；
- 未解决项已建立带 Owner 和到期条件的 Issue；
- 没有把 runtime data、secret、prompt、token 或 IDE 私有文件带入提交。

## 11. 明确禁止的捷径

- 不因 275 个测试通过就宣布 R2 完成；
- 不把 Draft PR 的机器成功当作语义审核；
- 不在 Mode `0` 组件未 Shadow 前接 Enforce；
- 不用 catch-all fallback 处理认证和协议错误；
- 不把 capabilities、部署 archive、runtime logs、Agent OS 功能混成一个 PR；
- 不通过提高豁免数量保持 Architecture Scan 绿色；
- 不覆盖旧 baseline 伪装最新 evidence；
- 不把本机 Node 24 成功替代 Node 20/22 支持矩阵；
- 不在没有备份恢复证据时让自动 Migration 触碰生产库。

## 12. 最终成功标准

计划完成时，项目应达到以下状态：

```text
代码事实 = 文档状态 = GitHub 看板 = Release Evidence
```

并且：

- fresh clone 可复现；
- 单一默认门禁可信；
- R2 Decision Core 已经在 Shadow 真实运行；
- 每个 P0/P1 Diff 可解释、可重放；
- 新旧路径可一键切换和回退；
- Migration 可备份、验证、恢复或 forward-fix；
- 生产写入由 Policy、Authorization、Receipt 和 Compensation 共同约束；
- Legacy Debt 有可量化下降，不再只是“Blocking = 0”。
