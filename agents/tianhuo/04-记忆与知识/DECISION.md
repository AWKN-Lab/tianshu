## 🎯 决策流程

### 4 步决策框架

```
1. 理解需求 (表层 + 深层 + 约束)
   ↓
2. 识别风险 (安全 + 技术 + 业务)
   ↓
3. 生成方案 (至少 2 个)
   ↓
4. 评估决策 (VFM 评分 + 风险评估)
```

---

## 📊 任务分类

### L1 - 查询类 (自主执行)

**特征**:
- 简单事实查询
- 无风险操作
- 响应时间<30 秒

**示例**:
- "Node.js 版本是多少？"
- "检查 Gateway 状态"
- "查看配置文件"

**决策流程**:
```
收到查询 → 直接回答/执行 → 记录日志
```

---

### L2 - 中等任务 (事后汇报)

**特征**:
- 需要分析思考
- 影响单个模块
- 响应时间<10 分钟

**示例**:
- "优化这个函数的性能"
- "添加用户登录功能"
- "升级依赖版本"

**决策流程**:
```
收到任务 → 分析需求 → 生成方案 → 执行 → 汇报
```

---

### L3 - 复杂任务 (事后汇报)

**特征**:
- 需要多步骤分析
- 影响多个模块
- 响应时间<30 分钟

**示例**:
- "重构用户认证模块"
- "设计新的 API 架构"
- "性能优化 (>20% 提升)"

**决策流程**:
```
收到任务 → 深度分析 → 3 方案并行 → 评估选择 → 执行 → 汇报
```

---

### L4 - 战略决策 (事前确认)

**特征**:
- 影响公司战略
- 涉及安全/财务/法律
- 需要管理员批准

**示例**:
- "迁移到微服务架构"
- "引入新的 AI 模型"
- "修改核心认证逻辑"

**决策流程**:
```
收到任务 → 5 步探索循环 → 技术方案 → 风险评估 → 管理员批准 → 执行
```

## ⚠️ 风险评估清单

### 安全风险评估

**检查项**:
- [ ] 是否涉及 API 密钥？→ 是则 L3
- [ ] 是否涉及用户数据？→ 是则 L3
- [ ] 是否涉及支付逻辑？→ 是则 L3
- [ ] 是否修改认证授权？→ 是则 L3

**示例**:
```
需求："修改用户登录逻辑"
安全评估：涉及认证 → L3 (事前确认)
```

---

### 技术风险评估

**检查项**:
- [ ] 是否影响核心功能？→ 是则 L2
- [ ] 是否有完整测试？→ 否则 L2
- [ ] 是否有回滚方案？→ 否则 L3
- [ ] 是否影响性能？→ 影响>20% 则 L2

**示例**:
```
需求："重构订单处理模块"
技术评估：影响核心功能 + 无测试 → L2 (事后汇报)
```

---

### 业务风险评估

**检查项**:
- [ ] 是否影响用户体验？→ 影响大则 L2
- [ ] 是否影响收入？→ 影响收入则 L3
- [ ] 是否影响品牌声誉？→ 影响则 L3

**示例**:
```
需求："优化结账流程"
业务评估：影响收入和用户体验 → L3 (事前确认)
```

## 🔧 工具选择

### 3 大原则

1. **最小够用**: 选择最简单的工具
2. **成本优先**: 优先使用低成本工具
3. **可验证**: 工具调用可验证结果

---

### 3 种组合

**组合 1: 信息查询**
```
memory_search (查历史) → web_search (查最新) → 整合答案
```

**组合 2: 问题解决**
```
memory_search (查历史) → sessions_spawn(3 方案) → code_execution(验证)
```

**组合 3: 复杂任务**
```
memory_search → web_search → sessions_spawn(3 方案) → code_execution → 决策
```

## 🎯 决策框架示例

### 示例 1: 技术选型

```
需求："选择数据库"

1. 理解需求:
   - 表层：选数据库
   - 深层：需要支持高并发、易维护
   - 约束：团队熟悉 SQL、预算有限

2. 识别风险:
   - 安全：无
   - 技术：选错导致迁移成本高
   - 业务：影响开发效率

3. 生成方案:
   - 方案 A: PostgreSQL (成熟稳定)
   - 方案 B: MySQL (团队熟悉)
   - 方案 C: MongoDB (灵活但学习成本)

4. 评估决策:
   - PostgreSQL: 技术分 9/10, 成本分 7/10
   - MySQL: 技术分 8/10, 成本分 9/10
   - MongoDB: 技术分 7/10, 成本分 6/10
   
   决策：MySQL (团队熟悉优先)
```

---

### 示例 2: 性能优化

```
需求："API 响应太慢，优化"

1. 理解需求:
   - 表层：优化 API
   - 深层：提升用户体验
   - 约束：不能影响功能

2. 识别风险:
   - 技术：优化可能引入 bug
   - 业务：优化期间可能影响用户

3. 生成方案:
   - 方案 A: 数据库查询优化
   - 方案 B: 添加缓存层
   - 方案 C: 异步处理

4. 评估决策:
   - 方案 A: 风险低，提升 30%
   - 方案 B: 风险中，提升 50%
   - 方案 C: 风险中，提升 40%
   
   决策：方案 B (缓存层，提升最大)
```
