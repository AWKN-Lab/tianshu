## C（Check）

### 6. 原因分析（5Why）

**问题 1：为什么一个"活着"的服务实际是孤儿，且 55 天无人发现？**
1. 为什么误判归属？→ 盘点时按服务名/目录名猜测（hindsight≈教练知识库），没看调用方代码
2. 为什么没看调用方？→ 下了"不能删"的结论后先入为主，不再验证
3. 为什么先入为主？→ 服务器上服务多（8 项目 + 基础服务），盘点追求覆盖速度，牺牲了证据深度
4. 为什么牺牲证据深度没被纠正？→ 缺少"服务价值 = 消费端"的判定准则，进程/端口在监听就被当成"在用"
5. **根因**：服务价值判定缺消费端证据链——"活着"≠"被用"，判定归属靠猜而非 grep 代码

**问题 2：为什么 hatwin 集成失败能静默 55 天？**
1. 为什么没报错？→ retriever 超时→返回空→回退关键词搜索，业务路径"正常"
2. 为什么能回退？→ 降级设计把集成失败消化成正常路径
3. 为什么没人发现？→ 无连接失败告警、无监控
4. **根因**：静默降级 + 无监控 = 故障隐形。集成失败被设计成"看不见"，比报错更危险

**可控因素**：消费端代码、监控、我们的判定方法（可控，已修）
**不可控因素**：hindsight 当初的构建动机与停更原因（不可完全还原）

### 12. 沉淀与复用

**SOP 1：服务价值判定**
找消费者 = grep 代码引用 + 三要素对齐（host/port、资源名、协议端点）；三要素任一错位即无连接；全 /opt 无引用 = 孤儿候选，走归档而非"留着再说"。

**SOP 2：PG 库归档五步**
应用代码取 PGPASSWORD → `pg_dump -Fc` → scp 本地 → SHA256 双方校验 → 停服务+disable → DROP → 验证端口与依赖健康。

**SOP 3：删除前端口扫描**
`grep -rln <port> /opt --exclude-dir=node_modules`，确认无外部引用再停服务。

**原则**
1. "活着"≠"被用"——服务价值由消费端定义，不由进程状态定义
2. 静默降级 = 故障隐形；集成失败必须显式（日志/告警），比静默回退好一万倍
3. 被用户纠正时，立即重启证据链，不辩解、不捍卫旧结论
4. 备份先行 + 双向 SHA256，再做任何破坏操作

**可迁移经验**
- 经验 1 → 适用：任何"清理/去重/优化"任务。先问"谁在消费它"，再谈怎么清
- 经验 2 → 适用：任何集成联调。连接失败要能看见，否则故障静默
- 经验 3 → 适用：任何删库删服。应用代码里的连接串是最可靠的凭据与拓扑来源

**下次先做 3 件事**
1. 判归属先 grep 消费端代码，不靠服务名猜
2. 动任何服务前先做端口/文件引用扫描（排除 node_modules）
3. 备份先行 + 双向 SHA256 校验，再执行破坏操作
