# EXP-DRV-20260723-009 — goal-manager updateGoal 绕过状态机标记 achieved（约束绕过 = 假成功）

- **类型**: derived（推导经验，人工沉淀）
- **日期**: 2026-07-23
- **触发**: 用户要求"实现完整的自主、自动、自进化的闭环 /goal" — 审查 goal/goal-manager.ts 时发现 updateGoal 标记 achieved 不检查 canTransition
- **作者**: AI + 用户监督
- **严重度**: 高（模型可绕过 budgetGate 预算约束 + 用户暂停，强行标记完成）
- **状态**: 已提炼

## 1. Bug 描述

`runtime/src/goal/goal-manager.ts` 的 updateGoal 标记 achieved 时直接赋值，不检查状态机：

```typescript
// 原版（bug）
if (patch.state === 'achieved') {
  goal.state = 'achieved';  // ← 不检查 canTransition
}
```

**问题**：`GOAL_TRANSITIONS` 明确限制以下转换非法：
- `paused → achieved`：GOAL_TRANSITIONS['paused'] = ['active', 'unmet']
- `budget_limited → achieved`：GOAL_TRANSITIONS['budget_limited'] = ['active', 'unmet']
- `unmet → achieved`：GOAL_TRANSITIONS['unmet'] = ['active']

但 updateGoal 绕过了状态机，让这些非法转换静默成功。

**影响**：
1. `budget_limited → achieved`：budgetGate 判定预算超限（假失败方向），模型却用 updateGoal 绕过预算约束直接标记完成 → budgetGate 的预算约束形同虚设 → 假成功方向
2. `paused → achieved`：用户暂停了目标，模型却标记完成 → 违反用户意图

对比：pauseGoal / resumeGoal 都正确检查了 canTransition，唯独 updateGoal（最关键的"标记完成"操作）漏检。

## 2. 修复

```typescript
// 修复后
if (patch.state === 'achieved') {
  if (!canTransition(goal.state, 'achieved')) {
    this._audit(
      'update_goal',
      { id, patch },
      false,
      `Cannot transition from '${goal.state}' to 'achieved' (state machine violation)`,
    );
    return null;
  }
  goal.state = 'achieved';
}
```

修复后：非法转换返回 null + 记录 audit log，与 pauseGoal/resumeGoal 行为一致。

## 3. 根因分析

### 表层原因
updateGoal 直接赋值 state，没调 canTransition。

### 机制原因
GoalManager 有三个状态变更方法：
- `pauseGoal` — 检查 canTransition ✓
- `resumeGoal` — 检查 canTransition ✓
- `updateGoal`（标记 achieved）— 不检查 ✗

模式不一致：前两个走了状态机，第三个绕过了。这是"同一职责的多个入口，约束不一致"问题。

### 根因
**约束只在部分入口生效 = 约束可被绕过**。状态机约束（GOAL_TRANSITIONS）是 goal 状态变更的统一规则，但只在 pauseGoal/resumeGoal 实现，updateGoal 漏了。任何能改 state 的入口都必须走状态机校验，否则约束形同虚设。

更深一层：这是"假达停止条件"假成功方向的第三种形态：
- E80/E81/E85：无信号当成功（fail-open / 不检查 terminated）
- **E87（本经验）：绕过约束当成功**（不检查 canTransition，直接赋值）

两者结果相同（错误地标记成功），但机制不同：前者是"没检查信号"，后者是"有约束但没走约束校验"。

## 4. 待提炼的铁律（候选，待人工确认）

### E87（候选）— 状态变更必须通过状态机校验（约束不能有绕过的入口）

**适用场景**：任何有状态机（GOAL_TRANSITIONS / state machine）约束的实体，且有多入口变更状态。

**规则**：
- 所有能变更 state 的入口（方法 / API / 工具）都必须走 canTransition 校验
- 不能只在一个入口检查，其他入口直接赋值
- 校验失败时必须拒绝（返回 null / throw / error），不能静默成功
- 新增状态变更入口时，第一件事是接入状态机校验

**反例（错误做法）**：原 updateGoal 直接 `goal.state = 'achieved'`，绕过 canTransition。

**正例（正确做法）**：
- pauseGoal / resumeGoal：检查 canTransition → 失败返回 null
- 修复后的 updateGoal：检查 canTransition → 失败返回 null + audit log

### E88（候选）— 同一职责的多个入口，约束必须一致

**适用场景**：同一实体的状态变更有多个方法/入口（如 GoalManager 的 pause/resume/update）。

**规则**：
- 多入口变更同一状态时，所有入口的约束（权限 / 状态机 / 校验）必须一致
- 不能"前两个检查，第三个不检查"——漏检的入口就是绕过点
- 审计时：找到一个入口的约束，立即检查所有同类入口是否一致

**反例**：pauseGoal 检查 canTransition，updateGoal 不检查 → updateGoal 是绕过点。
