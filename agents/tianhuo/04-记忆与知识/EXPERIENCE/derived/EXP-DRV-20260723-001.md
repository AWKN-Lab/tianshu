### 2.1 停止条件三处假达成

| reviewGate | 默认 `passed=true`，注释说"由 agent-loop 调 LLM 执行"，但 agent-loop 主循环根本没调 | 永远 PASS |

### 2.2 PRD 一致性算法自评自满

1. hash 精确匹配（合理）

3. **需求文本前 20 字符出现**（病态）

策略 3 导致 LLM 把 PRD 需求文本复述到 plan/docs 即可让 consistency=1.0，使算法退化为"自评自满"。

## 5. 经验提炼

### E73 — L2 停止条件必须用"否定证据"而非"默认通过"

**适用情境**: 任何设计 LLM 自主循环停止条件时。

**铁律**: 停止条件中的每一项 gate 必须用"否定证据"原则 — 默认 FAIL，只有 caller 提供真实证据（review verdict / cicd-tester 输出 / 测试通过）才转 PASS。禁止用"默认通过 + 注释说由别处执行"的偷懒设计，这必然退化为永远 PASS。

**反例**:
```ts
return { name: 'reviewGate', passed: true, details: '由 agent-loop 调 LLM 执行' };
```
注释说"由别处执行"，但别处根本没调，永远 PASS。

**正例**:
```ts
if (!ctx.reviewVerdict) {
  return { name: 'reviewGate', passed: false, details: '未提供 review verdict' };
}
const verdict = parseReviewVerdict(ctx.reviewVerdict);
return { name: 'reviewGate', passed: verdict === 'PASS' };
```
没有证据就 FAIL，强制 caller 必须真实调用。

### E74 — LLM 自评 LLM 必须用结构化标记而非文本相似度

**适用情境**: PRD 一致性、plan 验收等 LLM 产出对 LLM 产出的检查场景。

**铁律**: 检查 LLM 产出是否覆盖 PRD 时，禁止用"文本前 N 字符出现"这类模糊匹配。LLM 几乎必然复述 PRD 部分文本，导致算法退化为自评自满。

**正确策略**:
- 强制要求 LLM 在产出中明确引用 ID（US-xxx / AC-xxx）才算覆盖
- 或用 hash 精确匹配（要求逐字复述特定结构化片段）
- 模糊文本匹配只能用于"提示用户手动复核"，不能用于自动判定 PASS

### E75 — 文档 [x] 必须有可重放的命令证据

**适用情境**: 任何项目的设计方案 / 实施计划 / STATUS 文档勾选时。

**铁律**: 文档中 `[x] 已完成` 必须附带"可重放的命令证据" — 即任何人 clone 仓库后跑一条命令就能验证。禁止用"循环代码没崩溃"冒充"跑通"。

**反例**:
```
- [x] 真实任务跑通场景A（minimax 401 降级 trae 桥接，循环逻辑验证通过）
```
"循环逻辑验证通过"≠"achieved=true"。EXP-DRV-20260710-001 实测 achieved=false。

**正例**:
```
- [ ] 真实任务跑通场景A
  - 验证命令: `cd runtime && node dist/cli.js orchestrate tianhuo-cicd --goal "..."`
  - 期望: achieved=true 且 5 项 gate 全 PASS
  - 实测: achieved=false（详见 EXP-DRV-20260710-001）
  - 阻塞: minimax API key 401
```
