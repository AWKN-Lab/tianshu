# EXP-DRV-20260723-006 — hook-manager fail-open bug（安全钩子静默放行 + "无信号当成功"模式提炼）

- **类型**: derived（推导经验，人工沉淀）
- **日期**: 2026-07-23
- **触发**: 用户要求"实现完整的自主、自动、自进化的闭环 /goal" — M3 进阶-4 修复 trae stub 后，批判性深度分析 hook-manager.ts 发现同类 bug
- **作者**: AI + 用户监督
- **严重度**: 中（潜在安全风险，需 opt-in 才暴露；与 M3 进阶-4 同类模式，故独立沉淀为"模式经验"）
- **状态**: 已提炼

## 1. Bug 描述

`runtime/src/core/hook-manager.ts` executeCommandHook 在 command 输出非 JSON 时默认 `success:true`：

```typescript
// 原版（bug）
try {
  const parsed = JSON.parse(stdout) as Partial<HookResult>;
  resolve({
    success: parsed.success ?? true,  // ← 缺 success 字段也当成功
    ...
  });
} catch {
  resolve({
    success: true,  // ← 非 JSON 输出也当成功
    output: stdout,
  });
}
```

**问题**：
1. 命令崩溃/输出垃圾/缺字段 → 都被当作"成功"
2. 对 pre_tool_use 安全钩子风险最大：broken safety hook 静默放行危险工具（如 rm -rf）
3. 与 M3 进阶-4 trae stub 同类："无信号"被当作"成功"
4. 违反 Loop Engineering 铁律 2"循环里必须有说不的"

## 2. 修复

```typescript
// 修复后：opt-in failClosed 字段
export interface Hook {
  // ... 原有字段
  failClosed?: boolean;  // 新增
}

// executeCommandHook 内：
if (hook.failClosed === true && !hasSuccessField) {
  resolve({
    success: false,
    block: hook.point === 'pre_tool_use' ? true : undefined,
    blockReason: `failClosed hook missing "success" field`,
    error: 'failClosed hook missing "success" field',
    output: stdout,
  });
  return;
}
// catch 块同上：failClosed=true 时 fail-closed
```

修复后：
- 安全钩子可 opt-in `failClosed:true`，broken 时 fail-closed（pre_tool_use 阻断工具）
- 默认行为不变（向后兼容 informational hooks，如日志/统计）
- failClosed hook 输出合法 JSON（含 success）时不误伤

## 3. 根因分析

### 表层原因
hook-manager 的 catch 块和"缺字段默认值"都用了 `success:true`，没区分"信息钩子"和"安全钩子"。

### 机制原因
Hook 接口最初设计为"钩子失败不阻断主流程"（informational 用途），所有默认值都是 fail-open。后来 pre_tool_use 钩子增加了 `block:true` 安全语义，但默认值没同步更新 — 安全语义和 fail-open 默认值产生冲突。

### 根因
**接口的"默认安全姿态"必须按用途区分**，不能用统一默认值。安全相关接口默认必须 fail-closed，信息相关接口默认可以 fail-open。原设计把两类混在一起用同一个默认值，导致安全钩子继承了信息钩子的 fail-open 默认。

## 4. 待提炼的铁律（候选，待人工确认）

### E81（候选）— "无信号不能当成功"模式

**适用场景**：任何接收外部信号（command 输出 / API 响应 / hook 回调 / 文件桥接 / IPC 消息）的接口。

**规则**：
- 当外部信号缺失/损坏/格式不符时，**不能默认当作"成功"**
- 必须区分两种安全姿态：
  - fail-open（默认）：信号缺失 → 视为"未决策"，继续主流程（适用于 informational 接口）
  - fail-closed（opt-in）：信号缺失 → 视为"失败"，阻断主流程（适用于 safety-critical 接口）
- safety-critical 接口必须显式 opt-in fail-closed 模式

**已识别的实例**：
| 实例 | 信号缺失时的原行为 | 修复后行为 | 严重度 |
|------|---------------------|------------|--------|
| trae.ts stub 兜底（EXP-DRV-005） | 返回 stub finishReason='stop' | throw error | 高 |
| hook-manager executeCommandHook（本经验） | 默认 success:true | opt-in failClosed → success:false + block | 中 |

**反例（正确做法）**：
- minimax.ts / codex.ts：API 失败时 `throw new Error(...)`，不返回 stub
- reviewGate / securityGate：无 verdict 时 `passed:false`，不默认通过
- verificationGate：无 evidence 时 `passed:false`

### E82（候选）— 接口默认安全姿态必须按用途区分

**规则**：接口的默认行为（fail-open vs fail-closed）必须按用途显式选择，不能用统一默认值。

- safety-critical 接口（pre_tool_use blocker / 权限检查 / 资源限额）默认 fail-closed
- informational 接口（日志 / 统计 / 监控）默认 fail-open
- 接口契约必须显式声明安全姿态，不能依赖"约定俗成"

**反例（错误做法）**：原 hook-manager 对所有 hook point 用同一个 fail-open 默认，pre_tool_use 安全钩子继承了 informational 钩子的 fail-open 行为。
