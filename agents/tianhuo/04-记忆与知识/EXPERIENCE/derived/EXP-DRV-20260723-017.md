## 3. 自审 bug 根因分析

### Bug 1（M1-自审-A）：writeResp 注释声称原子但实际非原子 — high

**原代码**：
```typescript
/** 写 resp 文件（原子写：先写 tmp 再 rename，避免 trae 读到半写文件） */
function writeResp(respPath: string, resp: BridgeResponse): void {
  const tmpPath = respPath + '.tmp';
  writeFileSync(tmpPath, JSON.stringify(resp));
  // rename 是原子的（POSIX + Windows NTFS）
  try {
    writeFileSync(respPath, readFileSync(tmpPath, 'utf-8'));  // ← 与直接 writeFileSync(respPath, ...) 等价
    rmSync(tmpPath, { force: true });
  } catch {
    writeFileSync(respPath, JSON.stringify(resp));
    rmSync(tmpPath, { force: true });
  }
}
```

**问题**：
- 注释/JSDoc 明确声称"原子写"和"rename"，但实际代码用的是 `writeFileSync(respPath, readFileSync(tmpPath, 'utf-8'))`
- 这等价于直接 `writeFileSync(respPath, JSON.stringify(resp))` —— 写入瞬间 trae 端可能读到半写文件
- tmp 文件写入后没有任何原子性收益
- **测试也"通过"了**：因为 mock 模式下内容小、写入快，半写窗口几乎观测不到 —— 这是"测试通过 ≠ 行为正确"的典型例证

**影响链**：注释/文档承诺原子性 → 审查者信任注释 → 不深入看实际 renameSync 调用 → 实际半写 race 在生产环境（大响应、IO 抖动）下偶发 → trae 端 JSON.parse 失败 → fallback 文件修复逻辑也 race → "无信号被当作成功"模式复活

**修复**：
```typescript
import { ..., renameSync, ... } from 'node:fs';

function writeResp(respPath: string, resp: BridgeResponse): void {
  const tmpPath = respPath + '.tmp';
  writeFileSync(tmpPath, JSON.stringify(resp));
  try {
    renameSync(tmpPath, respPath);  // ← 真正原子操作
  } catch {
    // fallback：rename 失败（如 Windows 上目标已存在），直接写
    writeFileSync(respPath, JSON.stringify(resp));
    rmSync(tmpPath, { force: true });
  }
}
```

## 5. 候选铁律

### E100：注释声称的保证必须与代码实际行为一致

**适用情境**：所有 JSDoc / 注释 / 文档声称的"行为保证"（原子性、超时、限流、重试、幂等等）。

**铁律**：注释 = 契约。注释中声称的"原子写"、"超时 N 秒"、"最多重试 K 次"必须与代码实际行为一致。不一致的注释比无注释更危险 —— 因为审查者会信任注释而不深入查代码。

**反例**：
```typescript
/** 原子写：先写 tmp 再 rename */
writeFileSync(tmpPath, ...);
writeFileSync(respPath, readFileSync(tmpPath, ...));  // ← 注释说 rename，实际是 read+write
```

**正例**：
```typescript
/** 原子写：先写 tmp 再 rename */
writeFileSync(tmpPath, ...);
renameSync(tmpPath, respPath);  // ← 注释与代码一致
```

**测试通过 ≠ 行为正确**：mock 模式下内容小、写入快，半写窗口几乎观测不到 —— 但生产环境大响应、IO 抖动下会偶发。**注释/契约审查必须独立于测试覆盖**：测试可能无法覆盖到注释承诺的所有属性（如 race 条件、极端延迟）。

**与 E96/E99 的关系**：
- E96 是 provider 层接收外部输入的 fail-closed（空 content 不当成功）
- E99 是工具层执行失败的 fail-closed（throw 而非返回字符串）
- E100 是注释/文档层的 fail-closed（注释承诺的属性必须真实实现）
- 三者构成"声明 vs 行为"一致性的三层防线：接口输入、工具输出、文档承诺
