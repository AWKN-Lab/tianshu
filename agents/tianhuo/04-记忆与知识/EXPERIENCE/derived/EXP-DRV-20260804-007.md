## 经验正文

### 问题/场景
本地验证 Git 钩子（pre-push / pre-receive / post-merge 等需要 stdin 喂 ref 行的钩子）时，开发者本能用 PowerShell `echo "...sha..." | ./.githooks/pre-push` 来模拟推送。但 PowerShell 5.1 的 `echo` 是 `Write-Output`，跨进程管道会保留 CRLF 转换 → stdin 喂给 bash 钩子的 SHA 行尾变成 `\r` → 钩子内 `git rev-list <sha_with_\r>...HEAD` 报"ambiguous argument"。看上去像钩子逻辑崩，实则是测试假象。

真实 `git push` 由 git 二进制给钩子 stdin 喂纯 LF（无 CRLF 转换），钩子逻辑本身无 bug，但被错误的测试输入误导。

### 核心结论/原则
1. **测试钩子 stdin 协议必须与真实 git 一致**：用 bash 原生 `printf` 或 here-doc 生成 LF 干净输入；PowerShell 任何形式的管道跨进 bash 都不可信。
2. **CRLF 注入是隐性 bug**：SHA 看起来对（视觉上前几位相同），实际尾巴带 `\r`；错误信息指向"ambiguous argument"会让人误以为是 `git rev-list` 本身的问题。
3. **测试失败先怀疑测试本身**：若钩子在真实 push 中可重现失败，再排查逻辑；若只在测试时崩，几乎一定是测试输入污染。
4. **测试命令可固化到 SOP**：把 `bash -c 'printf "refs/heads/<branch> <a> refs/heads/<branch> <b>\n" "$(git rev-parse HEAD)" "$(git rev-parse HEAD~1)" | ./.githooks/<hook>'` 写进部署/钩子调试文档。

### 适用范围
- 所有需要 stdin 喂 ref 行的 Git 钩子（pre-push / pre-receive / post-commit 等的 stdin 协议分支）
- 任何"PowerShell 跨进程管道 + bash 脚本读取"组合
- 在 Windows 上做 Git 钩子调试/验收的场景

### 反例
- 用 PowerShell `echo $sha | ./hook` 测试 → 注入 CRLF → 假阳性崩溃
- 用 `[Console]::OpenStandardInput()` 手动模拟 → 仍可能残留 PS 进程的 CRLF 设置
- 把 SHA 写到临时文件然后 `< file ./hook` → 文件 BOM/换行也需检查
- 看到"ambiguous argument"立刻去改钩子里的 git 命令 → 修错地方

### 验证方式
- 测试脚本里加 `od -c <stdin | head` 或 `xxd` 打印前几字节，确认无 `\r`
- 跑真实 `git push --dry-run --no-verify` 看钩子是否还崩（如果只在 echo 测试崩而 dry-run 绿 = 测试问题）
- 把测试命令固化到 .githooks/README 或 scripts/hooks-test.md 供下次复用

### 失效条件
- 钩子完全不依赖 stdin（如 commit-msg 读 $1 文件）→ 本经验不适用
- 所有测试环境迁到 bash-only shell（如 WSL）→ PowerShell 路径不再存在
- git 升级后给钩子 stdin 的格式变化 → 需重新核对 git 源码 `connect.c` / `run-command.c`

### 授权边界
- 仅是测试方法约束，不修改钩子逻辑本身
- 不改变 .githooks/ 内脚本对真实 push 时的行为（那是 git 喂 stdin 的路径）

### 建议目标
- 建议在 .githooks/README.md 或 scripts/hooks-test.md 增加"钩子本地测试标准命令"章节，给出 printf 模板
- 建议在 pre-push 钩子头部加 sanity check：`input=$(cat); echo "$input" | grep -q $'\r' && { echo "ERROR: CRLF in stdin"; exit 2; }`
