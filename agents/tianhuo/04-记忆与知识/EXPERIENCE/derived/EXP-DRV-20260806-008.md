# EXP-DRV-20260806-008｜依赖状态判断：以文件系统和包管理器证据为准

## 来源证据

门禁出现 `tsc`、`eslint` 不可执行时，表面现象相似，但可能分别来自依赖未安装、安装残缺、包名与脚本错配、工作目录错误或本地二进制未加入执行环境。

## 教训

判断依赖是否可用，不能依据历史安装记录、锁文件存在或“之前跑通过”。应查询当前工作目录的真实状态：包管理器依赖树、本地包目录、`.bin` 可执行文件和脚本声明必须相互一致。

## 真相查询顺序

1. 确认工作目录和实际使用的 `package.json`。
2. 查询 `npm ls <package>`，识别 missing、invalid 和 extraneous。
3. 检查本地包目录与 `.bin` 入口是否存在。
4. 核对脚本调用的工具是否在 dependencies/devDependencies 中声明。
5. 使用 clean install 或 clean checkout 复现，排除本机残留文件。

## 反例

```text
错误：package-lock.json 里有 TypeScript，因此 tsc 一定存在。
错误：本机上曾执行成功，因此 CI 也会成功。
正确：当前 checkout 的 package.json、npm ls、node_modules 和 .bin 四项一致后才判定依赖可用。
```

## 验证

- clean checkout + clean install 后全部门禁通过。
- 删除本地残留文件后，测试不会依赖未跟踪资产。
- 依赖残缺时，诊断能指出缺失包和实际工作目录。

## 授权边界

诊断阶段只读；重新安装依赖、清理 `node_modules` 和修改锁文件需要独立工程授权。

## 失效条件

当构建完全运行在不可变容器或 hermetic sandbox 中，并由制品摘要证明依赖完整性后，本经验可并入构建环境规范。
