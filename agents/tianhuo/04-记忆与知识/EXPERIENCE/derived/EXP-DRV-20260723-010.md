# EXP-DRV-20260723-010 — loop_state 检查点恢复（断点恢复）+ LIMIT 1 假设最新即想要

- **类型**: derived（推导经验，人工沉淀）
- **日期**: 2026-07-23
- **触发**: 用户要求"实现完整的自主、自动、自进化的闭环 /goal" — M3 进阶-1~13 修完所有"假达停止条件"类 bug 后，循环执行单元已可靠，但循环状态只在内存 → 进程崩溃状态全丢 → 推进"自主"必须做断点恢复
- **作者**: AI + 用户监督
- **严重度**: 中（影响"自主"能力的可用性，但不影响正确性）
- **状态**: 已提炼

## 1. 缺口描述

M3 进阶-1~13 修完所有"假达停止条件"类隐藏 bug 后，循环执行单元（agent-loop / prd-centric-loop / cron-engine）已经可靠。但 L1 循环的状态（reactState / messages / turn / totalTokens）只在内存中维护：

- 进程崩溃 → 状态全丢
- L2 重启时 → 之前的 L1 进度无法恢复，必须从头跑
- L3 定时任务 → 长 L2 任务无法跨进程边界续传

这意味着 awkn 引擎只能跑短任务，长任务必须人工监督重启 → 不满足"自主"。

## 2. 实现

### 2.1 设计选择

- **复用 dead schema**：`loop_state` 表在 schema.ts 中定义了但从未被使用（注释明确"简化：只用内存 auditLog"）。直接复用其 `react_state` 字段存复合 JSON 快照，避免 schema 迁移。
- **复合 JSON 快照**：`LoopSnapshot` 包含 reactState + messages + turn + totalTokens + finalText + terminated，能完整恢复 L1 状态。
- **条件启用**：只在 `goalId` 存在时保存 checkpoint（L2 上下文才需要持久化），无 goalId 的纯 L1 不写 DB，避免污染。

### 2.2 接入点

`agent-loop.ts runL1` 接入 checkpoint：

- 每轮工具执行后 `saveCheckpoint()`
- LLM 失败 continue 前 `saveCheckpoint()`（崩溃后能从失败点续传）
- 所有 4 个 return 路径都 `clearCheckpoint(true, reason)`
- resume 时立即 `saveCheckpoint()` 一次（见 §3.2）

`runL2` 接入：

- 首次循环前 `loadLatestForGoal(goalId)` 检查可恢复 checkpoint
- 有则传给 `runL1({ resumeFrom: snapshot })`，消费后清空
- 后续 L1 调用走全新 L1（前一轮 L1 已 clearCheckpoint）

### 2.3 设计原则：clearCheckpoint 标记而非删除

`clearCheckpoint(id, terminated, reason)` 不删除行，而是更新 `react_state` JSON 中的 `terminated: true`：

- 保留审计轨迹（可查"哪些 L1 跑过、何时终止、为什么终止"）
- `loadLatestForGoal` 跳过 terminated 行
- `listResumable` 过滤 terminated 行

## 3. 实施中发现的两个隐藏陷阱

### 3.1 陷阱 1：`loadLatestForGoal` 的 SQL LIMIT 1 假设最新即想要

原版实现：
```typescript
loadLatestForGoal(goalId: string) {
  const row = queryOne<LoopStateRow>(
    'SELECT * FROM loop_state WHERE goal_id = ? ORDER BY updated_at DESC LIMIT 1',
    [goalId],
  );
  if (!row) return null;
  const snapshot = JSON.parse(row.react_state);
  if (snapshot.terminated) {
    // 直接返回 null，不再找更早的未终止 checkpoint
    return null;
  }
  return { id: row.id, snapshot };
}
```

**Bug**：用 `LIMIT 1` 只查最新一行，若该行 terminated 就直接返回 null。但同一 goal 可能多个 checkpoint（不同 id），最新一个被 clearCheckpoint 标记 terminated 后，更早的未终止 checkpoint 完全被忽略 → L2 无法 resume。

**根因**：SQL `LIMIT 1` 隐含假设"最新一条就是想要的"，但实际需求是"最新一条未终止的"。这两个条件在 terminated 行存在时分歧。

**修复**：改为查所有行按 updated_at DESC 排序，迭代返回第一个未 terminated 的。

### 3.2 陷阱 2：resume 后立即 saveCheckpoint 的必要性

`runL1(resumeFrom)` 接入 checkpoint 后，第一个测试失败：

```
AssertionError: checkpoint 应仍存在
  actual: null, expected: true
```

原因：测试用 `maxTurns=2`，turn 从快照的 2 开始，进入 while 条件 `2 < 2` → false，循环不进入。直接走 session_stop + clearCheckpoint。但 checkpoint 行从未被 saveCheckpoint 创建过 → clearCheckpoint 找不到行 → DB 中无记录 → loadCheckpoint 返回 null。

**修复**：resume 时立即 `saveCheckpoint()` 一次。这有两个作用：
1. 让本次 resume 留痕（覆盖之前的快照，updated_at 刷新）
2. 保证后续 clearCheckpoint 能找到行（即使 while 循环不进入也能正常标记）

## 4. 待提炼的铁律（候选，待人工确认）

### E91（候选）— 循环执行单元必须有 checkpoint 持久化机制

**适用场景**：任何长生命周期的循环执行单元（agent loop / pipeline / workflow）。

**规则**：
- 循环状态（messages / turn / tokens / intermediate state）必须能持久化到非易失存储
- 进程崩溃后能从 checkpoint 恢复，无需从头跑
- checkpoint 保存时机：每轮工具执行后 + 关键状态变更点
- checkpoint 失败必须 fail-open（不影响业务逻辑），但记日志

**反例**：原版 L1 循环状态只在内存，进程崩溃全丢。

**正例**：M3 进阶-14 的 LoopStateManager，每轮保存到 SQLite loop_state 表。

### E92（候选）— "查最新一条"的 SQL 不能假设最新即想要

**适用场景**：用 `ORDER BY ... DESC LIMIT 1` 查最新一条记录，且查询条件有过滤维度（如"未终止"）。

**规则**：
- `LIMIT 1` 隐含假设"最新一条就是想要的"
- 当过滤维度（如"未终止"）和排序维度（updated_at DESC）冲突时，LIMIT 1 会错过更早但满足过滤条件的记录
- 正确做法：把过滤条件放进 SQL WHERE 子句（如 `WHERE terminated = 0`），或查所有行迭代过滤
- 不能"查最新一行 → 内存判断 → 不满足就返回 null"

**反例**：
```sql
SELECT * FROM loop_state WHERE goal_id = ? ORDER BY updated_at DESC LIMIT 1
-- 然后内存判断 snapshot.terminated，true 就返回 null
```

**正例**：
```sql
SELECT * FROM loop_state WHERE goal_id = ? ORDER BY updated_at DESC
-- 然后迭代找第一个未 terminated 的
```
