# EXP-DRV-20260806-003｜服务价值由消费端定义："活着"≠"被用"——判归属用三要素对齐，不靠名字猜

**状态**: DRAFT
**类型**: DERIVED
**适用范围**: 任何服务器清理/服务盘点/去重任务中判定"这个服务/库/进程属于谁、能不能删"的场景
**关联 commit**: 无

## 教训

2026-08-06 服务器盘点把 hindsight（3.2G PostgreSQL 记忆系统）误判为"凌扬 AI 教练知识库，不能删"。用户纠正（hatwin 是程掌柜·酒店投资）后深挖，发现 hindsight 是孤儿系统：唯一的"消费者" hatwin retriever 存在三重错位——host:port（8888 vs 8890）、bank 资源名（hatwin-knowledge vs fitness-knowledge）、协议端点（REST recall 未注册，仅 MCP 有）全部不匹配，从未连通，静默降级 55 天。数据 56% 重复摄入、consolidation 停摆 55 天。最终备份归档删库，释放 3.0G。

- 证据 1：`hatwin-retriever.js` 调 8888/hatwin-knowledge/REST recall，实际服务只有 8890/fitness-knowledge/MCP recall——三要素全错位
- 证据 2：误判来源是服务名猜测（hindsight≈教练知识库），全程没有 grep 任何调用方代码
- 证据 3：grep /opt 全盘后 8891（LLM 代理）只有 hindsight 自用 → 确认孤儿
- 证据 4：553 文档仅 242 唯一 content_hash（56% 重复摄入），且唯一 bank 是 fitness-knowledge，hatwin 要的 bank 从未创建

## 反例

```text
错误：服务在运行 + 端口在监听 → "它在被用" → 保守保留 → 磁盘持续被孤儿占用
正确：判归属 = 找消费者 = grep 代码引用 + 三要素对齐（host/port、资源名、协议端点）
     → 任一错位即无连接 → 全盘无引用 = 孤儿候选 → 备份归档再删
```

## 验收

- 清理类任务判定归属时，必须给出 grep 调用方代码的证据，禁止以服务名/目录名推断
- 判"在用"必须三要素（host/port、资源名、协议端点）全部对齐，缺一即标【疑似无连接】
- 全盘无消费者引用 + 备份落地方可归档删除
