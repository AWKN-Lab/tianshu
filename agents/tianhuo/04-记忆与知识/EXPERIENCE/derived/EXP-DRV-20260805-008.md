## 经验正文

### 问题/场景
Agent 经验进化系统的"评测口径修复"（如把 token 阈值从硬门禁改为告警）需要验证两件事：
1. **新口径下历史失败样本是否裁决反转** — 证明修复确实改变行为
2. **新口径下历史通过样本仍保持 PASS** — 证明修复不引入误判

传统验证法是"重跑真实回放"，但这需要真实 LLM 调用（AgentReplayRunner.run → model.invoke），耗时 + 费用 + 不确定性（同一 case 不同次调用可能得到不同指标），且无法做"修复前 vs 修复后"的对照（同一次调用结果不可复现）。

### 核心结论/原则
**生产 DB 的留痕（evolution_evaluations.baseline_metrics_json / candidate_metrics_json / delta_json）本身就是"回放输入的完整快照"，可以直接喂给修复后的 evaluate() 完成裁决反转验证，无需真实 LLM**。

**标准三步法**：
1. **DB 副本隔离**：`cp production/awkn-engine.db tmp/awkn-engine-verify.db`，通过 `AWKN_DB_PATH` 环境变量让 evaluate() 读副本（不污染生产）
2. **历史 metrics 提取**：从 evolution_evaluations 表读取 baseline_metrics_json / candidate_metrics_json，构造 mock ReplayRunner（按 case 顺序返回对应 metrics，active 参数决定返回 baseline 还是 candidate）
3. **修复前后对照**：同一份 metrics 喂给"修复前 evaluate()" 与 "修复后 evaluate()"，对比 verdict/reasons/warnings

**核心优势**：
- 零 LLM 成本（不需要调用 model）
- 零环境依赖（不需要真实 runner / 工具链 / 网络）
- 可复现（同一份 metrics 永远产生同一 verdict）
- 真实数据边界（用的是生产 DB 留痕，不是合成数据）
- 可做修复前后对照（同输入、同口径变量）

### 适用范围
- 任何"评测口径/门禁判定逻辑"的修复验证（replay-evaluator、governance、shadow traffic evaluation、A/B testing framework）
- 任何"聚合指标 → verdict 裁决"的代码改动验证
- 任何"历史裁决结果需要在新口径下重判"的场景（裁决反转审计、回溯分析）
- AWKN Runtime 的所有 evaluator 类（replay、shadow、production evaluation）

### 反例（必须避免的设计）
1. **直接重跑真实回放** — 耗时 + 费用 + 不可复现，无法做修复前后对照
2. **合成 mock 数据** — 不能反映真实数据分布，可能漏掉边界 case
3. **用生产 DB 直接跑** — 会污染生产数据（状态机迁移、留痕覆盖）
4. **不区分 baseline/candidate 的 runner 实现** — 必须按 evaluate() 内部 `runner(case, null) vs runner(case, candidate)` 的语义区分返回值

### 验证方式
- 修复验证脚本模板（TypeScript / Node）：
  ```typescript
  // 1. 隔离 DB
  const tmpDb = '/tmp/awkn-verify.db';
  fs.copyFileSync(productionDb, tmpDb);
  process.env.AWKN_DB_PATH = tmpDb;
  
  // 2. 提取历史 metrics
  const db = new Database(tmpDb);
  const evaluations = db.prepare(
    `SELECT candidate_id, baseline_metrics_json, candidate_metrics_json 
     FROM evolution_evaluations WHERE verdict = 'FAIL'`
  ).all();
  
  // 3. mock runner
  const runner = async (case, active) => active 
    ? JSON.parse(row.candidate_metrics_json)
    : JSON.parse(row.baseline_metrics_json);
  
  // 4. 跑修复后的 evaluate
  const evaluator = new ReplayEvaluator(db);
  for (const row of evaluations) {
    const result = await evaluator.evaluate(row.candidate_id, runner);
    // 断言：旧 FAIL → 新 PASS + warnings 含 token
  }
  ```
- 验证清单：① 3/3 历史 FAIL 样本裁决反转；② baseline/candidate metrics JSON 原样保留；③ warnings 留痕完整；④ 终态 status=APPROVED
- 副作用检查：production DB 未被修改（hash 对比）

### 失效条件
- 历史 metrics 不完整（baseline_metrics_json / candidate_metrics_json 字段为空）→ 回退到真实重跑
- 修复涉及 case 集合变化（不是判定逻辑）→ 真实重跑
- 修复涉及模型行为（不是指标聚合）→ 不适用本方法
- 生产 DB 留痕被加密/脱敏导致 metrics 无法解析 → 提取后做 schema 校验

### 授权边界
- 仅约束"评测口径修复"的验证方法选择，不替代真实重跑的合理性（修复后必须做一次真实重跑作为生产保险）
- DB 副本仅用于验证脚本，不进入生产部署
- 历史 metrics 仅用于裁决反转验证，不用于训练或回流
