## 经验正文

### 问题/场景
lint / 校验工具常有两类对称操作：
1. **文件收集**：匹配磁盘上的文件（如 `*.md`、`EXP-*.md`、特定命名规则）
2. **引用提取**：在内容文本中扫描引用（如 markdown 链接、JSON 字段值、目录索引）

如果两个正则**独立演化**且**不对称**，会出现两类雷：
- **文件侧更宽**：引用侧提取了未收集文件 → 报"引用指向不存在文件" → 假阻塞
- **引用侧更宽**：文件侧收集了未引用文件 → 报"漏索引"但通常只是 warning，不阻塞（更安全）

check-markdown-assets.js 的初版恰好踩中第一种雷：INDEX.md 写一个 `EXP-DRV-...` 引用 → 文件收集找到该文件 → 通过；但只要 INDEX 写一个 `EXP-FOO-...`（任何大写类型），引用侧匹配而文件侧不收集 → 立刻阻塞推送。

### 核心结论/原则
1. **双向正则单一真源**：lint 工具内"找文件"和"找引用"必须共享一个常量定义的正则（或同一表达式的两个变体如带/不带 `\b`）；禁止两份独立正则字面量。
2. **收集/提取对称性**：两份正则应严格等价（同一字符集、同一锚定、同一长度约束），否则差异即潜在雷。
3. **不对称时偏向"引用侧窄"**：若两份正则因语义必须不同，应让引用侧 ≤ 文件侧（宁可漏报 false negative，不可误报 false positive 阻塞推送）。
4. **常量化便于审查**：`const EXP_ID_PATTERN = '...'` 在文件顶部显著位置，配合注释说明哪两类操作共用它。
5. **lint 工具自检**：可在工具输出增加"正则哈希 / 常量路径"提示，便于审查与排错。

### 适用范围
- 所有 lint / 校验 / 检查类工具（Markdown 检查、JSON schema 校验、依赖审计、配置 lint 等）
- 所有"既扫描文件系统又扫描文本内容"的对称操作
- 任何"匹配文件命名 + 匹配内容引用"的双重匹配场景

### 反例
- 文件收集用 `^EXP-DRV-.*\.md$`，引用提取用 `EXP-[A-Z]+-\d+` → 引用侧类型集更宽 → 假阻塞
- 两份正则字面量散落在 walk() / scan() / match() 等不同函数里 → 各自演化无强约束
- 收集用严格正则（带 `\b` / 行尾 `$`），提取用宽松正则（无锚定） → 边界 false positive
- 把"漏索引"作为阻塞 error（应仅 warning）→ 把可恢复的设计问题变成不可恢复的推送阻塞

### 验证方式
- 工具首版落地前，针对"已知会触发但应放行"的样本集跑一次（如 INDEX 引用 `EXP-FOO-...`，但 `EXP-FOO-...` 不在跟踪范围内 → 必须不阻塞）
- 在测试用例中加"跨类型引用"样本：故意让 INDEX 引用未跟踪类型，验证仅 warning 而非 error
- 代码审查时强制要求 lint 工具顶部出现 `const X_PATTERN = '...'` 常量定义
- grep 工具内同义正则：`grep -nE "EXP-[A-Z]" scripts/check-*.js` 看是否有多个独立字面量

### 失效条件
- 引用侧与文件侧语义本就要求不同（如"忽略某些已知 ID"是设计意图）→ 必须有显式排除列表 + 注释
- 工具维护期允许临时偏差但需 TODO + 注释
- 工具退役或被新工具取代 → 本经验随之失效

### 授权边界
- 仅约束 lint 工具自身代码风格与正则设计，不影响业务逻辑
- 不替代业务侧对"哪些 EXP 类型应被跟踪"的决策（应来自 agents/ 域约束）

### 建议目标
- 已修复: agents/tianhuo/scripts/check-markdown-assets.js（新增 `EXP_ID_PATTERN` 常量，提交随 fix(harness) 链路合并）
- 建议在 agents/tianhuo/scripts/ 下其他 check-*.js 工具（check-core-code.js 等）也走"双向正则单一真源"模式
- 建议在 lint 工具评审清单中加入"正则字面量数量"检查（>2 个独立正则视为风险信号）
- 建议 INDEX 一致性规则统一为："漏索引"= warning（不阻塞），"悬空引用"= error（阻塞）
