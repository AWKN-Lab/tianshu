## 2. 错误文本（Bug 描述）

`CronEngine.stop()` 设置 `this.running = false` + `clearTimeout` 所有已注册 timer + `clearInterval(checkInterval)`。
但若某 job 的 `setTimeout` callback **正在执行**（`await this.executeJob(job)` 尚未完成），
callback 完成后会调用 `this.scheduleJob(updated[0])` 调度**新 timer**。

`scheduleJob` 原版**不检查 `this.running`** → 新 timer 被加入 `this.timers` →
新 timer 在 delay 后触发 → `executeJob` 在 engine "已停止"状态下仍执行 →
执行后再 `scheduleJob` → **无限链式调度**。

**现象**：`running=false`（看似已停止），但 timer 持续触发 job（实际未停止）→ "假停止"。

**当前未触发原因**：CLI 的 `cron start` 在 `stopCronEngine()` 后立即 `process.exit(0)`，
进程死亡，zombie timer 无意义。但编程式用法（`startCronEngine() → ... → stopCronEngine() → 继续其他工作`）
会暴露此 bug。

## 3. 根因分析

### 为什么会发生

1. **`stop()` 只清理"已注册"的调度，不阻断"未来"的调度**
   - `clearTimeout` 取消已排队但未触发的 timer
   - `clearInterval` 取消兜底轮询
   - 但**无法取消正在执行的 callback**（JS 不可取消 Promise/async function）

2. **`scheduleJob` 没有 `running` 守卫**
   - `stop()` 清理 `this.timers` map（`this.timers.clear()`）
   - 但 callback 中的 `this.scheduleJob()` 会**重新添加**到已清空的 map
   - 新 timer 不在 `stop()` 清理范围内

3. **`setTimeout` callback 也没有 `running` 守卫**
   - `clearTimeout` 在极窄窗口（事件循环已拾取 callback 但 callback 尚未执行）下无效
   - callback 执行时 `this.running` 可能已为 false

### 与已有铁律的关系

这是 **E98（系统级自动状态转换不能豁免状态机检查）** 的变体：
- E98: `autoPauseIfBudgetLimited` 直接设 `goal.state = 'budget_limited'` 不检查 `canTransition`
- E103（本条）: `scheduleJob` 直接调度 timer 不检查 `this.running`

**共同模式**：状态标志变更（`running=false` / `state='budget_limited'`）必须能阻止后续操作。
若只设标志不检查标志，标志就是"装饰"而非"门禁"。

## 4. 修复方案

### 修复 1：`scheduleJob` 开头加 `running` 守卫

```typescript
private scheduleJob(job: CronJobRow): void {
  if (!this.running) return;  // ← 新增
  // ... 原有逻辑
}
```

### 修复 2：`setTimeout` callback 开头加 `running` 守卫（双重保险）

```typescript
const timer = setTimeout(async () => {
  if (!this.running) return;  // ← 新增
  await this.executeJob(job);
  // ... scheduleJob 也有守卫
}, delay);
```

### 为什么需要双重守卫

| 场景 | 第一道守卫（callback） | 第二道守卫（scheduleJob） |
|------|------------------------|--------------------------|
| stop() 在 callback 执行前 | clearTimeout 取消（正常） | 不需要 |
| stop() 在 callback 执行中（await 中） | callback 完成后 running=false → return | 不需要（callback 已 return） |
| stop() 在 callback 完成后、scheduleJob 前 | — | running=false → return |
| stop() 在极窄窗口（事件循环拾取 callback 但未执行） | running=false → return | 不需要 |

**关键洞察**：`clearTimeout` 无法取消"已被事件循环拾取但尚未开始执行"的 callback。
JS 的 setTimeout 不是真正的取消 — 它只是标记 timer 为 "cleared"，
但如果事件循环已经将 callback 放入执行队列，callback 仍会运行。
因此 callback 内的 `running` 检查是必要的兜底。

## 5. 提炼的铁律

### E103 — 状态标志变更必须阻断后续调度，不能只清理已注册的调度

**适用情境**：
- 任何有 `start()` / `stop()` 生命周期的组件
- 使用 `setTimeout` / `setInterval` / `requestAnimationFrame` 的调度器
- 有 "running" / "stopped" 状态标志的引擎

**铁律**：
`stop()` 必须**同时**：
1. 设置状态标志（`running = false`）
2. 清理已注册的调度（`clearTimeout` / `clearInterval`）
3. **在调度入口检查状态标志**（`scheduleJob` / callback 开头 `if (!running) return`）

只做 1+2 不做 3 → "假停止"：标志说停了，但正在执行的 callback 会调度新 timer，
新 timer 不在 `stop()` 的清理范围内 → engine 继续运行但标志显示已停止。

**反例（原版 bug）**：
```typescript
stop() {
  this.running = false;
  clearTimeout(...);  // 只清理已注册的
}
scheduleJob() {
  // ❌ 无 running 检查 → stop() 后仍可调度新 timer
  this.timers.set(id, setTimeout(...));
}
```

**正例（修复后）**：
```typescript
stop() {
  this.running = false;
  clearTimeout(...);
}
scheduleJob() {
  if (!this.running) return;  // ✅ 阻断 stop 后的新调度
  this.timers.set(id, setTimeout(async () => {
    if (!this.running) return;  // ✅ 双重保险
    ...
  }));
}
```

**manual override 例外**：`triggerJob`（手动触发）**不需要**检查 `running` —
用户显式触发是 override，应能在 stopped 状态执行（如调试时手动触发一个 job）。
