## 经验正文

### 问题/场景
任何被 Windows Git 钩子（pre-commit / pre-push / commit-msg / ...）显式调用的 PowerShell 脚本（.ps1），若以 `powershell.exe`（5.1）作为执行器，则脚本必须以 UTF-8 BOM 开头。原因：5.1 默认按系统 ANSI 代码页读取脚本文件，中文 Windows 系统即 GBK。无 BOM 时：
- 纯英文脚本：通常可通过（GBK 与 ASCII 兼容）
- 含中文（注释/字符串/参数值）：被转码为乱码 → 关键字破坏 → 解析失败（try/finally、here-string、`-match`、`$_` 等都可能中招）

Git 在 Windows 默认通过 `core.hooksPath` 指向的脚本本身不强制编码，但调用栈中的 `exec powershell.exe -File ...` 会把脚本读入 5.1 引擎，5.1 走 ANSI 路径。

### 核心结论/原则
1. **钩子引用的 .ps1 一律带 BOM**：被 `.githooks/*`、CI 矩阵、Windows 计划任务等显式调用的所有 .ps1，首字节必须是 EF BB BF；新文件用 `New-Object System.Text.UTF8Encoding($true)` 写盘。
2. **5.1 是最弱基线**：默认 Windows Git 钩子执行器即 5.1，不要假设 `pwsh.exe`（7）一定可用，除非在钩子里显式调 `pwsh.exe -File ...`。
3. **测试矩阵必须覆盖 5.1**：本地门禁验证须用 `powershell.exe`（非 pwsh 7）执行钩子流程，避免"开发机用 pwsh 7 跑通、用户机器用 5.1 跑崩"。
4. **含中文的 PS1 必查 BOM**：对历史遗留无 BOM 且含中文的 .ps1，加 BOM 是最低风险修复（不改语义、不改逻辑）。

### 适用范围
- 所有在 Windows Git 钩子中被 `powershell.exe` 或 `powershell` 调用的 .ps1
- 推广到 GitHub Actions 中 `shell: pwsh` 之外的 Windows matrix 任务
- 推广到任何"含中文注释 + 默认 5.1"组合的脚本场景

### 反例
- 假设 Windows 已统一升级 pwsh 7 而拒绝加 BOM → 用户机器旧版 5.1 即崩
- 仅给执行器加 `-Encoding UTF8` 参数，但脚本仍无 BOM → 5.1 读 ANSI 阶段仍先于 -Encoding 解析
- 改用 `chcp 65001` 后不加 BOM → 代码页切换只影响输出/输入流，不改变脚本本身的解析编码

### 验证方式
- 用 `powershell.exe -NoProfile -File <script>.ps1` 执行（不带 pwsh），能正确输出中文且无解析报错
- 用十六进制工具查看 .ps1 头三字节：`EF BB BF` = 有 BOM；`23 23 23`（###）= 无 BOM（风险信号）
- 在 hooks 仓库里加 `git diff --check` 之外的 BOM 校验（CI 步骤）

### 失效条件
- Windows Git 钩子改为显式调用 `pwsh.exe`（7）且所有用户机器已统一 7+ → BOM 必要性下降但不会破坏
- 脚本改为不含中文且全 ASCII → 5.1 ANSI 解析可通过，BOM 仍推荐保留（一致性）

### 授权边界
- 仅修改脚本文件首字节 BOM，不改脚本逻辑；不改 .githooks/ 调用方式（除非确认所有用户机已 pwsh 7）
- 不强制给所有项目内 .ps1 加 BOM，仅约束"被钩子/CI/计划任务调用"的脚本

### 建议目标
- 已修复: scripts/local-ci.ps1（加 EF BB BF，提交 89d5bcb 已推送）
- 建议在 .better-harness 或 local-ci 脚本里增加"BOM 体检"步骤，对 hooks 引用的 .ps1 做二进制首字节校验
- 建议与既有 memory `PowerShell 5.1解析含中文UTF-8脚本需BOM` 合并并升级为"全项目门禁规则"
