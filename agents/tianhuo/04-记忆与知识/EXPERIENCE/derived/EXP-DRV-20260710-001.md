## 问题

Phase 4 两个 L2 Goal-based 验证场景（天火+CICD多agent协作 / PRD核心优化循环）需要从设计伪代码落地为可运行代码。关键挑战：
1. 跨模型 review 需要 AgentLoop 支持 per-instance provider，但原代码不支持
2. orchestrator 编排器需要组合多个 AgentLoop + 评估停止条件
3. PRD 一致性评估需要确定性算法，不能靠 LLM 自评

---

## 可复用模式

### 1. per-instance provider 透传模式

**问题**：AgentLoop 需要按实例指定 LLM provider（跨模型防互认同），但原代码只能通过环境变量全局切换。

**解法**：router 已支持 `req.provider` 显式指定，只需 AgentLoopConfig 加 `provider?: LlmProvider` 字段，在构造 ChatRequest 时透传。

```typescript
// AgentLoopConfig
provider?: LlmProvider;

// runL1 内
const req: ChatRequest = {
  // ...
  provider: this.config.provider,  // 透传
};
```

**要点**：provider 是 optional，不传时走 router 默认逻辑，零破坏现有 L1/L2 循环。

### 2. orchestrator 编排器模式

**问题**：多 agent 循环需要组合多个 AgentLoop + 评估停止条件 + 回填反馈。

**解法**：orchestrator 不直接调 LLM，通过构造 AgentLoop 实例 + 调 runL1 实现。

```typescript
while (cycle < maxCycles) {
  const agentResult = await new AgentLoop({ provider: 'trae', systemPrompt }).runL1(prompt + feedback);
  const reviewResult = await new AgentLoop({ provider: 'codex', systemPrompt }).runL1(reviewPrompt);
  const stopEval = await evaluateStop({ cicdTesterVerdict: reviewResult.finalText });
  if (stopEval.achieved) { gm.updateGoal(goalId, { state: 'achieved' }, 'model'); return; }
  feedback = reviewResult.finalText;  // 回填
}
```

**要点**：
- 每轮构造新 AgentLoop 实例（避免状态污染）
- 打回原因回填给下一轮的 prompt
- goal state 变为 'achieved' 才算成功
- updateGoal 的 actor 参数只接受 `'model' | 'user'`，不能传 `'orchestrator'`

### 3. PRD 一致性确定性评估模式

**问题**：PRD 一致性不能靠 LLM 自评（会"自评自满"），需要确定性算法。

**解法**：hash 交集匹配 + 关键词包含双策略。

```typescript
// 1. 从 PRD 抽取需求（正则匹配 US-xxx: / AC-xxx: / 验收标准:）
// 2. 每项算 sha256 hash
// 3. 匹配策略：hash 精确匹配 OR 需求ID出现 OR 需求文本前20字符出现
// 4. 一致性 = |已覆盖| / |总需求|，>= 0.8 通过
```

**要点**：三重匹配策略应对非结构化产出，hash 保证确定性。

### 4. skillTool 内联 vs 独立工具模式

**问题**：场景B 的 orchestrator 需要调用 awkn-* 技能，是做成 builtin tool 还是内联函数？

**解法**：两者都做。
- 内联 `callSkill()` 函数：orchestrator 直接调用，不走 tool registry
- 独立 `skillTool`：注册到 builtinTools，让 agent-loop L1 循环中也可调用

```typescript
// 内联（orchestrator 用）
async function callSkill(skillName, input, cwd) {
  const body = sm.getSkillBody(skillName);
  const loop = new AgentLoop({ systemPrompt: body });
  return loop.runL1(input);
}
```

### 5. 文档状态同步模式

**问题**：方案文档的 checkbox 状态严重滞后于实际代码，会误导后续工作判断。

**解法**：每次代码实现完成后，立即更新方案文档对应 checkbox。

**要点**：Phase 2 实际已完成 v6.3 但文档标 `[ ]`，Phase 3 实际已完成 90%+ 但文档标 `[ ]`。文档与代码不一致是执行检查的常见陷阱。

## 避坑清单

1. **updateGoal actor 参数**：只接受 `'model' | 'user'`，不能传自定义字符串如 `'orchestrator'`
2. **dynamic import 的 tsc 检查**：cli.ts 用 `await import('./orchestrator/xxx.js')` 时，模块必须存在否则 tsc 报 TS2307
3. **builtin 工具数组顺序**：新增工具要加到 `builtinTools` 数组，否则不会被 agent-loop 加载
4. **goal state 终态检查**：achieved/unmet 是终态，不可再改，orchestrator 循环前要检查 `goal.state !== 'active'`
5. **existsSync 未使用 import**：预先存在的 TS6133 错误会阻塞 tsc，需清理

### 三方案可行性最终结论

| 方案 | 可行性 | 原因 |
|------|--------|------|
| MCP | ❌ 不可行 | TRAE IDE/CLI 是 MCP 客户端不是服务端，方向反了 |
| ACP/智能体 | ❌ 不可行 | traecli 未安装，TRAE IDE 不暴露 ACP 接口给外部进程 |
| 文件协议桥接 | ✅ 可行 | trae.ts 三层 fallback（hook → 文件桥接 → stub）已验证 |

### 文件桥接协议要点

1. **req/resp 文件格式**：`req-{id}.json`（runtime 写）/ `resp-{id}.json`（宿主写）
2. **resp JSON 格式**：`{"id":"...", "content":"...", "usage":{...}}`，content 中**不能含字面换行符**，必须用 `\n` 转义
3. **轮询参数**：2s 间隔，120s 超时（60 次轮询）
4. **清理职责**：runtime 读 resp 后删 req+resp；宿主写 resp 后删 req
5. **"拉"模式**：无自动监听，需手动触发或脚本轮询
