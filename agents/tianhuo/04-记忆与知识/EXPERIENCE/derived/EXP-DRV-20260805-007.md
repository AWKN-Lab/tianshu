## 经验正文

### 问题/场景
Agent 经验进化系统（ReplayEvaluator）对候选规则做回放评测时，判定 PASS/FAIL 的门禁集合里既包含"质量性指标"（successRate、errorRate、securityViolationRate、humanTakeoverRate），也包含"成本性指标"（tokenCount、cycles）。旧实现把所有指标同等塞进 reasons 数组，任一超限即 FAIL → QUARANTINED。

**致命陷阱**：候选规则文本会被 `AgentReplayRunner.run()` 拼入 system prompt（`CANDIDATE_ENGINEERING_RULE ... END_CANDIDATE_ENGINEERING_RULE` 块），导致候选侧 tokenCount 必然包含规则文本本身的固定注入开销。规则越长、token 增量越大，越容易触发 token 比值超限 → **用自己的输入开销否决自己的输入**。

### 核心结论/原则
**评测门禁必须二分类**，分类后再决定是否进入 verdict：

1. **裁决性主门（decision-grade）**：决定 verdict 的硬门禁
   - 质量性：successRate、errorRate、securityViolationRate、humanTakeoverRate
   - 主门违反 → reasons.push → verdict=FAIL → 状态机切到 QUARANTINED
   - 原则：**主门永远是质量性指标，与候选输入成本无关**

2. **告警性超限（advisory-grade）**：仅留痕、不裁决
   - 成本性：tokenCount、cycles、单轮耗时
   - 超限 → warnings.push → 不影响 verdict，仅写入 evolution_evaluations.delta_json 供成本观测与人工复核
   - 原则：**任何"受候选自身输入污染"的指标都不能进入裁决向量**

**反例/正例对照**：
- ❌ `if (tokenRatio > 1.1) reasons.push('token cost regressed')` — token 比值 = 1.53、successRate=1 却被 QUARANTINED
- ✅ `if (tokenRatio > 1.1) warnings.push('token cost exceeded warning ratio')` — token 仍留痕、verdict 仅看主门
- ❌ `if (cycleRatio > 2.0) reasons.push('cycle count regressed')` — 同理，cycles 也被 prompt 长度污染
- ⚠️ 复杂场景：若 cycles 异常暴涨但 successRate 不变，可能是规则让 agent 反复检索/重试 → 应进 reasons（行为回退）；若 cycles 微增但 successRate 同步提升，可能是规则让 agent 更谨慎 → 应进 warnings

### 适用范围
- 任何 A/B 实验、回放评测、沙盒评估、规则/配置/代码候选的自动化裁决
- 任何"基线 vs 候选"的指标对比
- 任何"指标聚合 → 二元裁决 → 状态机迁移"的链路
- AWKN Runtime（replay-evaluator / governance / lifecycle）、agent 评测框架、A/B testing 平台、shadow 流量评估

### 反例（必须避免的设计）
1. **成本指标与质量指标混在同一裁决向量** — 本次修复正是这种
2. **候选侧注入成本未做归一化** — 必须区分"规则文本引入的固定开销"与"行为变化引入的可变开销"
3. **告警性指标无留痕** — warnings 必须写入 delta_json 留痕，否则失去成本观测能力
4. **主门与告警用同一阈值** — 主门阈值应严格（< 5% 回退），告警阈值应宽松（> 30% 才告警）

### 验证方式
- 任意评测修复必须做"裁决反转验证"：取历史上被旧口径裁决 FAIL/QUARANTINED 的样本，用新口径重跑，统计裁决反转率（PASS 化率）
- 留痕边界保持：evolution_evaluations 表结构不变；delta_json 保留所有原始指标；新增 warnings 字段为可选
- 测试覆盖三类场景：① 告警超限但主门全过 → PASS + warnings；② 主门回归 + 告警超限 → FAIL + warnings 但 reasons 不含告警；③ 留痕边界完整（baseline/candidate/warnings/thresholds 全部入表）
- 边界探针：故意构造"被注入开销污染但主门全过"的真实候选样本（如本次 23d54fdc），验证 verdict 反转

### 失效条件
- 当成本指标与质量指标完全独立（候选侧注入成本已扣除 / 指标定义已排除输入长度影响）→ 可恢复为单一裁决向量
- 当告警性指标本身成为业务红线（如"绝对禁止超过 X token"的安全/合规约束）→ 升级为主门
- 当业务方主动要求"成本硬门禁"（如预算约束）→ 显式声明为硬门禁，但必须同步声明"候选侧注入成本归一化策略"

### 授权边界
- 仅约束评测系统自身的裁决向量设计，不替代业务方对成本/质量权重的判断
- 修复时必须先确认业务方意图：是"成本硬门禁"还是"成本告警"？含糊时按"告警"处理（保守原则）
- 主门 vs 告警的分类需写明在 EvaluationThresholds 配置注释中，运维可见

### 建议目标
- 在 AWKN Runtime 的 evaluation-evaluation.md 文档中固化"主门 vs 告警"分类原则
- 在 replay-evaluator.ts 的 EvaluationThresholds 接口注释中明确每个字段属于"主门"还是"告警"
- 把本次修复的设计选择（token 降级为 warnings）写入 governance skill（governance-evaluation skill）的门禁设计章节
- 月度回顾：扫描历史 evolution_evaluations，统计"被 token 单独裁决"的失败案例占比；若 >10% 则触发一次"门禁二分类审计"
