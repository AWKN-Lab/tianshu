# AWKN-执行检查 v2.0.1

> **核心理念**：**上下文 + 目标 + 约束 + 验证 = 稳定的 AI Coding**
>
> 任何对已有项目的修改，必须经过 Read→Locate→Plan→Patch→Verify 五步检测。
>
> **v2.0.0 升级**: 从"手工检查"升级为"自动化+可执行+持续巡检"的工程级执行检查。
> 新增: 变更影响分析引擎 + 跨项目变更追踪 + 活文档与知识图谱 + 可执行验证套件 + 执行度量与漂移巡检

---

## 一、定位

| 做 | 不做 |
|---|---|
| 修改已有项目前的强制前置检测 | 新项目从零创建（归 awkn-prd） |
| 五步检查制 + 自动化影响分析 | 实际写代码（归 awkn-工程师） |
| 变更影响半径评估 + 漂移巡检 | 正式代码审查（归 awkn-审核） |
| 可执行验证套件 + 活文档生成 | 部署上线（归 awkn-部署） |
| 跨项目/多仓变更追踪 | 流程调度（天阶功法） |

## 二、五步流程（紧凑摘要）

```
Step 01 Read    → 先读项目（建立上下文）     + 生成依赖快照 + 文档新鲜度检查
Step 02 Locate  → 定位范围（明确影响）       + 自动影响分析 + 爆炸半径评估
Step 03 Plan    → 输出计划（确认方案）       + 风险评分自动计算 + 命令盘点三件套
Step 04 Patch   → 小步修改（原子执行）       + 即时验证 + 不顺手优化
Step 05 Verify  → 验证结果（确认完成）       + 可执行验证套件回归 + 度量记录
```

### Step 01 Read — 先读项目 + 知识图谱生成

| 动作 | v1.x 手工 | v2.0 工程化 |
|------|----------|-----------|
| 浏览项目结构 | 手动 `ls`/`tree` | 自动生成 ASCII tree |
| 识别依赖关系 | 手动 grep | **依赖图自动生成** (madge/pydeps) |
| 理解架构 | 读文件+脑记 | **知识图谱** + 架构快照 |
| 文档核验 | 无 | **文档新鲜度检查** (>30天→STALE) |
| 代码审计 | require一致性/大文件/占位符 | 同 v1.x + 架构边界断言 |

**通过标准**: 能用一句话说清项目做什么、怎么跑、核心逻辑在哪 + 依赖图已生成。

### Step 02 Locate — 定位范围 + 影响分析

| 动作 | v1.x 手工 | v2.0 工程化 |
|------|----------|-----------|
| 列变更文件 | 手动列清单 | **自动影响分析** (依赖图 × grep) |
| 评估风险 | 人工判断 | **爆炸半径评估** (L1/L2/受影响API/测试) |
| 画影响范围 | 手动树形图 | **变更传播路径可视化** (Mermaid) |

**铁律 1**: 变更前必跑影响分析。风险评分 ≥ 高 → 强制走标准模式。

**通过标准**: 改动文件清单 + 爆炸半径 + 传播路径全部输出。

### Step 03 Plan — 输出计划 + 风险量化

**7 要素输出**: 相关文件 / 当前逻辑 / 影响模块 / 推荐方案 / 不建议改的 / 可能风险 / 验证方式

**v2.0 增强**:
- 风险等级基于爆炸半径自动计算
- 命令盘点三件套 (tsc + test + dist) 锁定清单完整性
- 高风险改动强制标准模式

### Step 04 Patch — 小步修改（原子执行）

**4 策略**: 明确最小目标 / 逐文件修改 / 即时运行验证 / 确认无影响

**铁律**: 不顺手重构、不顺便格式化、不顺便"优化"。每个逻辑点独立 commit。

### Step 05 Verify — 验证结果 + 可执行回归

**v2.0 增强**: 运行可执行验证套件（tests/understanding/），每个"理解"对应一个可执行断言。

**三态结论**: PASS / PASS_WITH_RISKS / FAIL

## 三、四种执行模式

| 模式 | 流程 | 适用场景 |
|------|------|---------|
| **标准模式** | R→L→P→P→V 完整五步 | 功能开发、需求变更 |
| **快速模式** | R→L→P→V（合并 Patch+Verify） | 紧急 bug 修复（风险≤低时可用） |
| **计划模式** | R→L→P（只输出计划不执行） | 方案评审、影响评估 |
| **Spec 对标模式** | Diff→L→P→P→V | 按外部 spec/checklist 改造 |

**模式选择规则**: 风险评分 ≥ 高 → 标准模式（禁止快速模式）。

## 七、先读后写校验（Alice 方法论）

**铁律**: 任何文件修改操作前，必须先执行 Read 操作。

| 场景 | 拦截条件 | 恢复动作 |
|------|---------|---------|
| SearchReplace 未先 Read | 当前会话未读取目标文件 | 先 Read 再 SearchReplace |
| Write 覆盖未先 Read | 当前会话未读取目标文件 | 先 Read 再 Write |
| 批量修改多个文件 | 任一文件未读取 | 逐个 Read 后再修改 |

**豁免**: 新建文件 / 配置文件初始化 / 自动生成的文件

## 八、跳步检测规则

| 触发条件 | 跳过了 | 级别 |
|---------|--------|------|
| 未读文件直接修改 | Read | 🔴 阻塞 |
| 未列文件清单直接改 | Locate | 🔴 阻塞 |
| 未输出计划直接改 | Plan | 🔴 阻塞 |
| 一次修改超过 5 个文件 | Patch | 🟡 警告 |
| 修改后未验证 | Verify | 🔴 阻塞 |
| 顺手重构/格式化 | Patch | 🟡 警告 |
| 高风险改动无回滚方案 | Plan | 🔴 阻塞 |
| **变更前未跑影响分析** | Locate (v2.0) | 🔴 阻塞 |
| **理解无可执行证据** | Read (v2.0) | 🟡 警告 |

## 九、上下游衔接

```
awkn-prd (需求) → [awkn-执行检查] (本技能) → awkn-工程师 (Build) → awkn-审核 (Review) → awkn-部署 (Ship)
```

**v2.0 新增衔接**:
- 执行检查的**度量数据** → awkn-审核的**模式库**（变更失败模式共享）
- 执行检查的**可执行验证套件** → awkn-cicd 的**Pipeline 测试阶段**（回归测试共享）
- 执行检查的**活文档** → awkn-审核的**文档反向同步门控**（文档一致性共享）

## 十、铁律汇总

| # | 铁律 | 反例 |
|---|------|------|
| 1 | **变更前必跑影响分析** | 改了一个 utils 函数，不知道 15 个文件依赖它 |
| 2 | **理解必须有可执行证据** | Step 01 输出"用了 React + Context"但没有验证脚本 |
| 3 | 先读后写，不读不改 | 凭记忆改文件，覆盖了新代码 |
| 4 | 不顺手优化 | 顺手重构引入意外 bug |
| 5 | 计划不确认 = 盲改 | 计划写完不等确认就动手 |
| 6 | 高风险 = 标准模式 | 改数据库结构用快速模式 |
| 7 | 原子 commit，可回滚 | 一次改 10 个文件，出 bug 无法定位 |
