# 复盘与总结系统 V2（合并版）

> **来源**：玄策 V1 + review-report-writer (master) + 祥瑞 SKILL 编写最佳实践
> **定位**：把"总结、复盘、深度复盘"统一成一套长期稳定、可复用、可沉淀、可交付的工作系统

## 一、Skill 定位

本 Skill 用于完成三件事：
1. 把问题看清
2. 把经验沉淀下来
3. 把结果无缝传递到下一阶段

**不是单纯的"写总结"或"讲道理"，而是让每一轮工作都能带走方法、资产与下一步。**

## 三、总体原则（硬性要求，15 条）

1. **只基于事实与素材**：不编造；不确定就标【待确认】或【证据不足】
2. **结论先行**：先说最关键结论，再展开分析
3. **重点写异常、差距、关键节点**：避免流水账
4. **每个关键结论尽量配证据**：数据、日志、原话、反馈、现象、对比结果
5. **能量化尽量量化**：不能量化则用可观察现象描述
6. **必须落到动作**：下一步、负责人、截止时间、验收标准、风险预案
7. **必须形成资产**：SOP、模板、清单、规则、提示词、母文档、FAQ、判断标准
8. **不重复造轮子**：能复用的内容不重写，能在母文档上迭代的不重复堆上下文
9. **大事拆开做**：一件大事分阶段推进，每完成一段就做阶段总结与收口
10. **闭环优先**：不是"聊完了"，而是"带得走、接得上、能继续推进"
11. **商业底层逻辑优先**：每句话回答——为什么做、服务什么目标、商业价值是什么
12. **方法感优先**：多用思维方式、方法路径、结构化判断，不堆砌术语
13. **能判断就不追问**：已足够判断时直接推进，避免无效反问
14. **跨会话接力的最小化**：计划应一次性覆盖全量步骤，减少迭代版本。跨会话接力是不得已的妥协，必须最小化。优先选择"小步快跑 + 单会话闭环"而非"大步推进 + 多会话接力"
15. **验收必须区分"模块自包含 PASS"和"端到端接线 PASS"**：多 Phase / 多模块项目验收必须同时跑两套检查（service 自包含 + 入口接线），禁止合并表述"功能完成"
16. **复盘前自检**：启动复盘前必须完成 3 步——查 N 值（本对话第几次复盘？N≥3 时主动声明"复利开始显化"）+ 查版本（当前 SKILL 是否已覆盖？避免重复造轮子）+ 查对象（列 3 个可能的复盘对象让用户选择：代码/协作/决策）。无新增洞察时主动声明"无新增"，比写"水分经验"更有价值。来源：E-A25（复利闭环）+ E-A23（先确认对象）
17. **主-子智能体协作对账门禁**：主智能体调用 subagent（search / general_purpose_task）后，**必须**对子智能体输出做至少 1 次采样对账，再写入正式产物。
    - **触发场景**：所有 subagent 输出（路径、行号、组件名、统计数字）
    - **对账方法**：
      - 路径：取 1-2 个关键路径，用 Glob 或 LS 验证存在
      - 行号：取 1-2 个关键行号，用 Read 验证行号内容匹配
      - 组件名：取 1-2 个组件名，验证是否在 routes/components/ 中实际存在
      - 统计数字：取 1-2 个数字（如"120 路由"），用 Grep 计数验证
    - **对账失败处理**：
      - 标【待人工确认】+ 记录 subagent 输出
      - 不用 subagent 输出做主决策
      - 必要时自己用 Read 重新提取
    - **来源**：2026-06-02 三段式推进复盘 — Agent-A 报"StylePage 不存在"（实际存在，属幻觉）；未实质影响，但需列入门禁
    - **E33 细化（v2.4.4）**：4 个常见 subagent 输出类型必须对账
      1. **路径类**（如 `src/api/routes/chat.ts`）：用 Glob/LS 验证
      2. **行号类**（如"chat.ts:1150"）：用 Read 验证行号内容
      3. **组件名类**（如"StylePage 组件"）：用 Read 实际验证文件存在
      4. **统计类**（如"120 个路由"）：用 `Grep -c "router\.(get|post)"` 重新数

19. **元规则变更必须 L1+用户授权+变更记录**（v2.5.2 新增）：对 `.trae/rules/` 等元规则文件的修改，必须满足 3 个条件——
    - **L1 模式确认**：在权限分级中（当前为 L1 "AI 提议 + 用户确认"），不可越权
    - **用户主动授权**：用户明确说"修改规则"/"改权限"等指令才算授权，不能凭"看起来该改"
    - **变更记录段**：必须新增"八、变更记录"或类似段落，记录日期/变更/原因/授权
    - **触发词**：元规则 / 权限分级 / 规则变更 / .trae/rules / 配置保护 / L2 改 L1
    - **反例**：直接 `SearchReplace` 改 ai-permission-levels.md 而不加变更记录段 → 不算合规
    - **来源**：2026-06-02 awkn-agent V4 收尾时元规则 L2→L1 变更

20. **复盘比计划更重要 — 4 段式元规则**（v2.6.0 新增，源自 E72）：每完成 ≥2 天里程碑后 1 天内必须写复盘，复盘必须区分 4 段——
    - **承诺**（计划写了什么）
    - **验证**（实际做了什么）
    - **真实发现**（计划没写但执行中暴露的事 — 90% 价值在这里）
    - **调整下窗口**（用真实发现更新下次计划）
    - **触发**：任何 ≥2 天计划完成里程碑 / 收到"为什么没做 X"反馈
    - **反模式**：复盘拖到下个里程碑才写（错过窗口） / 复盘只写"做了什么"（漏掉"没做什么"） / 把复盘当计划文档（重复造轮子）
    - **强信号**：本次会话能自动识别"evolve 阶段缺失 → 补 5 个 E 经验" = E72 预测能力在第 1 次复现中**被部分验证**

### 默认思维方式（自然融入分析与表达）
- 商业底层逻辑
- 批判性思维
- 第一性原理

## 四、模块 A：总结（收口清单）

### 定义
总结不是"回顾一下"，而是：**把已经发生的东西，提炼成下一步还能直接用的东西。**
闭环不是"说完了"，而是：**让这一轮工作从目标出发，经过执行，最终变成可交付、可传递、可复用、可继续推进的状态。**

### 输出格式（默认 9 项）
1. 这轮目标是什么，完成到哪了？
2. 这轮产出了什么？
3. 这轮确认了哪些关键结论？
4. 这轮犯了哪些错，根因是什么？
5. 这轮有哪些有效解法可复用？
6. 这轮沉淀了哪些资料和资产？
7. 下一步是什么，入口条件是什么？
8. 哪些内容应进长期记忆，哪些留母文档？
9. 这轮让系统在哪些地方变得更强了？
10. 这轮的 handoff 交接文档是什么？（给下一个 AI / 下一次会话的关键上下文：当前进度、未完成项、关键决策、踩坑记录）

### 补充检查项（复杂场景时追加）
- **边界闭环**：明确哪些不做 / 暂缓 / 否决
- **版本闭环**：当前哪一版有效，上一版为何废弃
- **责任闭环**：下一步由谁推进
- **时机闭环**：什么时候再打开这件事
- **价值闭环**：这轮之后目标、用户价值、商业价值是否更清晰

## 五、模块 B：标准复盘

### 定义
用于分析一次事件、任务、项目、问题或决策，从目标到差距、从原因到动作，形成可复用的经验与对策。

### 输出格式（严格 10 步）

#### 第一步：问题定义
- 这次事件或问题的本质是什么？
- 核心矛盾在哪里？
- 成功状态是什么？

#### 第二步：目标与假设
- 当初的目标是什么？（显性与隐性目标分别列出）
- 成功的判断标准是什么？

#### 第三步：现状与差距
- 当前真实情况如何？
- 与目标的关键差距在哪里？
- 哪些是最重要的差距？

#### 第四步：原因分析
- 提出可能原因（MECE 拆分）
- 对原因进行优先级排序
- 选择最关键原因进行验证
- **必须包含三层**：
  - 表层原因（直接触发）：
  - 机制原因（流程/信息/协作/系统/能力层）：
  - 根因（如果不解决，下次还会复发的那一层）：

#### 第五步：证据与验证
- 用数据、事实、行为、日志进行验证
- 哪些假设成立？哪些不成立？
- 不确定的标注【待验证】

#### 第六步：策略与对策
- 可行解决路径有哪些？
- 哪条路径最优？优先级如何？

#### 第七步：风险与不确定性
- 可能出现的风险是什么？
- 哪些情况可能导致失败？
- 应对策略是什么？

#### 第八步：行动与实验
- 下一步具体行动是什么？
- 如何用最小成本验证？

#### 第九步：结果复核
- 如何判断是否成功？
- 验收标准是什么？（写成"看到什么=成功"，不要写"提升、优化"）

#### 第十步：沉淀与复用
- 可以沉淀哪些原则、模型、模板或 SOP？
- 哪些经验可迁移到其他场景？
- **强制回答**：下次遇到类似情况，先做哪 3 件事？

### 输出要求
- 优先用人话表达，避免术语堆叠
- 每一步都要有明确结论
- 原因分析至少深入到"机制原因"层
- 必须给出可执行动作和验收标准
- 每个关键结论配一条证据，证据不足标【证据不足】

### 定义
用于重大项目、连续失败、关键决策、复杂问题、系统性故障等场景。
**不是把标准复盘写长，而是：分析更深、证据更硬、机制更清楚、风险更完整、输出更可交付。**

#### 第一层：深度分析（增强版标准复盘 10 步）

1. **原因拆解加强**：至少拆到表层原因 / 机制原因 / 根因 **三层**，每层配证据

## 七、模块 D：复盘总结

### 定义 = 标准复盘 + 收口清单

### 默认输出顺序
1. 先输出标准复盘（10 步）— 模块 B

### 强制收尾句

### 9.2 复盘闭环流水线（核心机制）

> 复盘不是终点。复盘的真正价值在于让经验回流到系统，下次可自动激活。
> 来源：2026-05-20 剧本开发套件工程修复全流程验证

```
┌──────────┐    ┌──────────┐    ┌──────────────┐    ┌──────────────┐    ┌────────────┐
│ 1. 复盘  │ → │ 2. 提炼  │ → │ 3. 写入记忆   │ → │ 4. 回写技能   │ → │ 5. 激活    │
│ 发现问题 │    │ 可复用   │    │ 系统(L1/L2)   │    │ 系统          │    │ 下次任务   │
│ 分析根因 │    │ 经验/SOP │    │               │    │               │    │ 自动调用   │
└──────────┘    └──────────┘    └──────────────┘    └──────────────┘    └────────────┘
     ↑                                                                         │
     └─────────────────── 6. 新任务触发，经验已被索引 ←────────────────────────┘
```

| 步骤 | 做什么 | 落到哪里 | 产出物 |
|------|--------|---------|--------|
| 1. 复盘 | 发现问题、分析根因、总结得失 | 对话输出 | 复盘报告 |
| 2. 提炼 | 从复盘中提取可复用经验、SOP、框架 | 审核判断 | 编号经验（如 E9/E10/E11） |
| 3. 写入记忆 | 按 L1 项目经验 / L2 行为偏好归档 | `记忆系统/L1/` `记忆系统/L2/` | 经验文件 |
| 4. 回写技能 | 将新框架/SOP 更新到对应 AWKN 技能（含自身） | `awkn-审核/SKILL.md` `awkn-工程师/SKILL.md` 等 + 本技能 | 技能更新 |
| 5. 激活 | 下次类似任务触发技能时，新经验已被索引 | 技能路由 | 自动匹配 |

### 9.2.1 经验分流规则（经验→记忆 vs 经验→SKILL）

> 核心判断：这条经验是"记住它"还是"变成它"？

| 经验特征 | 去向 | 判断标准 | 示例 |
|----------|------|----------|------|
| 项目特定事实/数据 | → 记忆 L1 | 只在当前项目有用 | "剧本套件修复耗时3天" |
| 个人偏好/习惯 | → 记忆 L2 | 影响执行方式但不改规则 | "用户喜欢先看结论再看分析" |
| 可复用SOP/流程改进 | → SKILL.md | 改变了"怎么做"的规则 | "10步法第4步应强制三层原因" |
| 新判断规则/决策标准 | → SKILL.md | 改变了"怎么判断"的规则 | "素材不足时降级为初步观察" |
| 新模块/新触发场景 | → SKILL.md | 扩展了"做什么"的范围 | "新增异常降级策略模块" |
| 修复型教训（防复发） | → SKILL.md + 记忆 | 双写：SKILL加规则，记忆留证据 | "模板优先三步法" |
| 方法论/框架 | → SKILL.md | 改变了"怎么想"的框架 | "复盘前先画数据流" |

**分流决策树**：
```
这条经验是否改变"怎么做/怎么判断/怎么想"的规则？
    │
    ├── 是 → 写入 SKILL.md（对应章节）
    │         └── 同时写入记忆 L1/L2（留证据链）
    │
    └── 否 → 只写入记忆
              ├── 项目相关 → L1
              └── 通用偏好 → L2
```

### 9.2.2 自更新规则（经验→回写本技能SKILL.md）

> 闭环流水线第4步"回写技能"不仅回写其他技能，也必须回写本技能自身。

**触发条件**（满足任一即触发自更新）：
- 复盘中发现当前流程/原则/判断规则有缺陷或遗漏
- 使用中反复出现同一类异常，说明现有规则不够
- 用户反馈"应该先做X再做Y"且验证有效
- 新增的异常降级策略被验证≥2次
- 发现新的复盘场景/对象类型不在现有分类中

**更新映射表**（经验类型 → SKILL.md章节）：

| 经验类型 | 更新到哪个章节 | 更新方式 |
|----------|---------------|----------|
| 新触发场景 | 二、适用场景 | 追加口令映射行或场景触发项 |
| 新原则/修改原则 | 三、总体原则 | 追加编号原则或修改现有原则措辞 |
| 流程步骤改进 | 五/六、模块B/C | 修改步骤描述或追加子步骤 |
| 新判断规则 | 三、总体原则 或 对应模块 | 追加判断规则段落 |
| 异常降级策略 | 超时与异常处理 | 追加降级策略行 |
| 新沉淀资产类型 | 9.1 资产沉淀清单 | 追加资产类型 |
| 新复盘对象分类 | 二、复盘对象分类 | 追加分类项 |
| 输入字段补充 | 十七、输入字段说明 | 修改表格或追加行 |
| 不做什么补充 | 十六、不做什么 | 追加边界项 |

**自更新执行流程**：
1. 识别：复盘/使用中发现可改进点
2. 判断：按分流规则确认应写入SKILL.md
3. 定位：按更新映射表找到目标章节
4. 修改：最小改动（追加/修改措辞），不大改/重构
5. 验证：确认修改后SKILL.md结构完整、无截断、无矛盾
6. 记录：在CHANGELOG.md中记录本次更新
7. 升版本：frontmatter.version 递增（patch级：v2.1.0→v2.1.1）

**自更新约束**：
- 每次自更新只改1个章节，不跨章节大改
- 不删除现有原则/步骤，只追加或修改措辞
- 修改后必须验证SKILL.md可被正常读取和触发
- 涉及核心结构变更（新增模块/删除模块）需用户确认

**复利显化原则**（v2.5.4 新增）：

当同一 SKILL.md 在短时间内被多次自更新（N≥3），说明经验正在"复利累积"——每次复盘都发现新规则需要补充。此时应：
1. 主动声明"复利开始显化"（N≥3 时）
2. 评估是否需要**结构性升级**（minor 级 v2.5→v2.6）而非仅 patch 级
3. 检查是否有更高层原则需要提炼（多条 patch 经验可能指向同一个根因）

来源：awkn-agent P3+ 深度复盘（本技能 v2.4.1→v2.5.3 共 6 次 patch，指向"漂移预防"和"完成定义"两个根因）

**E57｜并行 subagent 精准目标隔离原则**（v2.5.5 新增）：

多个 subagent 并行修改不同文件时，只要目标"文件×章节"不重叠，天然零冲突——无需锁机制。

- **正例**：4 个 subagent 各改 4 个不同 SKILL.md → 0 冲突；经验分流表已确保"哪条经验→哪个技能"无重叠
- **反例**：2 个 subagent 都改同一个 SKILL.md → 赢者覆盖输者（awkn-agent v4 P0 收口事件）；未做经验分流就并行 → 部分经验被重复写入
- **触发词**：并行 subagent / 多个技能同时更新 / subagent 协调
- **来源**：2026-06-05 4 技能并行 patch 自更新流水线复盘

**E58｜SKILL 自更新不触发递归自更新**（v2.5.5 新增）：

本技能 SKILL.md 自更新时，若 §9.2.2 规则再次触发"本技能自更新"→ 死循环风险。

- **规则**：本技能 SKILL.md 每次自更新仅触发 1 次（patch 级），不触发递归更新
- **触发词**：SKILL 自更新 / 循环依赖 / 递归触发
- **来源**：2026-06-05 4 技能并行 patch 自更新流水线复盘（发现 §9.2.2 "本技能自更新"与"自更新触发自更新"的循环依赖风险）

## 十、与长期协作方式的衔接

- 不重复造轮子
- 母文档优先
- 一件大事拆开做，每完成一阶段就收口
- 对话中不丢目标与初心
- 能判断就不追问
- 工具调用遵循目标优先、先轻后重

## 十五、经验写入能力

已吸收 evolution-writer：当复盘中出现可复用经验、修复型教训、方法论沉淀或用户说"记住这个""写入记忆"时，自动触发经验写入流程。

### 写入触发条件（满足任一即触发）
- 复盘中产出可复用经验（SOP/模板/原则/判断规则）
- 修复型教训（错误→原因→解法→防复发）
- 方法论沉淀（框架/模型/路径/策略）
- 用户明确要求"记住这个""沉淀经验""写入记忆"

### 写入流程
1. **识别类型**：FIX（修复型）/ DERIVED（派生型）/ CAPTURED（捕获型）
2. **提取结论**：从复盘中提取核心结论（一句话）
3. **构建证据链**：结论 + 证据来源 + 验证次数 + 跨场景性 + 置信度 + 日期
4. **写入目标**：
   - 项目经验 → `记忆系统/L1/项目复盘/`
   - 行为偏好/通用经验 → `记忆系统/L2/`
   - 可复用框架 → 对应AWKN技能文件
5. **验证写入**：确认文件已更新，内容可被下次任务索引

### 证据链格式
```
- [结论] xxx
  - 证据：xxx（来源文件/任务/事件）
  - 验证次数：N
  - 跨场景：是/否
  - 置信度：high/medium/low
  - 日期：YYYY-MM-DD
```

### 不写入的情况
- 临时信息（仅本次有效）
- 无证据支撑的判断
- 与已有经验重复（去重后跳过）

### 15.1 derived 草稿自动补全流程（v2.6.2 新增）

> 来源：M3 自进化机制落地（EXP-DRV-20260723-002）— 闭环缺口：experience-writer 自动写草稿后无人补全根因，草稿堆积

**触发条件**（满足任一）：
- 启动复盘/经验沉淀时（默认扫描一次 derived 目录）
- 用户说"补全草稿"/"处理 derived"/"扫草稿"
- runtime session_stop hook 触发经验沉淀后（如 LLM provider 可用）

**扫描流程**：
1. 扫描目录：`agents/tianhuo/04-记忆与知识/EXPERIENCE/derived/`（项目根下）
2. 识别"待补全"草稿的标记（满足任一）：
   - 状态行含 `**状态**: 待人工补充`
   - 含 `## 4. 根因分析（待人工补充）` 标题
   - 含 `## 5. 待提炼的铁律（待人工补充）` 标题
3. 对每个待补全草稿：
   a. 读取第 1-3 节（背景/检测到的模式/样本证据/latestError）
   b. 用 LLM 能力分析根因（基于 pattern.kind + source + latestError + sampleIds）
   c. 补全第 4 节"根因分析"：
      - 替换"待人工补充"提示块
      - 写三层原因：表层（直接触发）/ 机制（流程/系统层）/ 根因（不解决会复发）
      - 每层配证据，证据不足标【证据不足】
   d. 起草第 5 节"待提炼的铁律"候选：
      - 基于根因提炼 1-3 条候选铁律
      - 每条按"适用情境 + 铁律 + 反例 + 正例"格式（参考 E73/E76）
      - 标注"候选，待人工确认"
   e. 更新状态行：`**状态**: 待人工补充` → `**状态**: 已起草根因（待人工确认铁律）`
   f. 在文件末尾追加：`_本文件根因部分由 awkn-复盘总结 v2.6.2 自动补全，铁律待人工确认。_`

**边界**（对应 E74 防 LLM 自评自满）：
- **铁律最终必须人工确认**，LLM 只起草候选，不能自动标"已提炼"
- **不自动关闭 corrections_ledger 记录**（writeExperience 已关闭同指纹记录，铁律确认是人工动作）
- **不自动升级状态到"已提炼"**——"已提炼"需要人工确认铁律后手动改
- **不修改第 1-3 节**（自动检测部分，由 experience-writer 生成，保持原样）

**写教训**：草稿堆积是因为 experience-writer 只能写不能补全。补全根因需要 LLM 推理，是 awkn-复盘总结 的职责。两个模块必须衔接，否则闭环卡在"起草"阶段。

**写反例**：草稿写完后无人处理 → derived 目录堆积 N 个"待人工补充"草稿 → 自进化闭环卡在"起草"阶段，永远不"提炼" → 系统反复犯同样的错却没人总结

**写触发词**：补全草稿 / 处理 derived / 扫草稿 / 经验沉淀 / session_stop / derived 草稿 / 待人工补充

## 十六、不做什么

## 十六点五、模块 F：洞穴人模式（来自 skills-main/caveman 融入）

### 定义
跳过一切格式和流程，用最粗暴的方式抓住关键信息。适合时间紧、脑子乱、只想快速出结论的场景。

### 触发条件
- 用户说"洞穴人复盘"/"caveman"/"粗暴复盘"
- 时间极度紧张（<5 分钟）
- 脑子一团乱，需要快速理清

### 输出格式（仅 4 项）

1. **发生了什么？**（3 句话以内）
2. **哪里出了问题？**（1 句话）
3. **怎么修？**（1-3 个动作）
4. **下次先做什么？**（1 句话）

### 洞穴人原则

- 不写废话，不写铺垫，不写"经过深入分析"
- 每个回答不超过 3 句话
- 如果说不清楚，说明还没想清楚
- 可以在洞穴人模式后升级为标准复盘（模块 B）

### 升级路径

```
洞穴人模式（5min）→ 标准复盘（30min）→ 深度复盘（2h）
        ↓                  ↓                  ↓
    抓住关键           系统分析           根因+防复发
```

## 十六点六、Recap 会话摘要（来自 agentmemory/recap 融入）

### 定义
在长会话或复杂任务执行过程中，定期生成交互摘要，防止上下文丢失。

- 会话已执行 > 10 轮对话
- 用户说"recap"/"回顾一下"/"刚才做了什么"
- 切换任务前
- 会话即将结束

### 输出格式

```markdown
## 会话 Recap

**会话目标：** [一句话]
**已完成：** [关键产出列表]
**当前状态：** [进行到第 N 步 / 第 N 次复盘]   ← v2.5.0 新增"复盘计数"

**踩坑记录：** [遇到的问题和解决方案]
**下一步：** [接下来要做什么]
```

### Recap 与复盘的区别

| | Recap | 复盘 |
|---|---|---|
| 目的 | 防止上下文丢失 | 经验沉淀和改进 |
| 深度 | 浅（事实罗列） | 深（原因分析） |
| 时间 | 随时，1-2 分钟 | 任务结束后，10-60 分钟 |
| 产出 | 摘要文档 | 复盘报告 + 经验写入 |
